# План mypi

Актуализирован 2026-10-02: решения [M0-CONTRACT](docs/M0-CONTRACT.md), принятая [политика тестирования](docs/TESTING.md) и уточнение [учёта запросов в M1](docs/M1-REQUESTS.md).
**Первый результат — система управления памятью и проектами на Node.js, включая
учёт запросов инженера и их состояния в БД. Исходник и материалы —
в папке задачи, история — в общем JSONL-журнале с ротацией, не в SQL-полях.
Без исполнения flow и сабагентов.**

Ниже чётко разделены история Python-прототипа и новая реализация. Прежний путь
«файловый request lifecycle → PostgreSQL → обязательный агентный workflow»
заменён; БД нужна с начала новой реализации, агентный workflow — не нужен.

## M1 — память и проекты на Node.js

Цель: самостоятельная полезная система, без Python backend и без оркестрации.
Реализация разрешена ответом «начинай» 2026-10-02, затем запрошен весь поэтапный цикл; [ход и проверки](docs/M1-CYCLE.md). Функциональные этапы реализованы; независимое статическое review выполнено, исправления подтверждены. M1 не закрыта: доверенный gate заблокирован из-за подменяемой идентичности check; [CI](docs/M1-CI.md).

Выбраны **pnpm** и **модульный монолит по предметным областям + Ports & Adapters +
сценарии внутри модулей**. Принятые границы и организация кода —
[M1-DESIGN.md](docs/M1-DESIGN.md), запись выбора — §10. Стек принят (§11):
**TypeScript strict, Node.js 24 LTS, ESM/tsc, SQLite + better-sqlite3,
SQL-миграции без ORM, node:test + node:assert/strict**. Минимальная схема, путь БД, partial-контракт и стартовые бюджеты приняты —
[M1-START.md](docs/M1-START.md). Версии зафиксированы, совместимость проверена на временных данных;
CLI/API всех модулей M1, локальный Git, импорт, backup/restore и ограниченный запуск реализованы.
CI/trusted gate и независимое review пока не настроены.
Простой учёт запросов входит в M1 — [M1-REQUESTS.md](docs/M1-REQUESTS.md).
Предметная основа БД: organizations/projects/requests/request_statuses. Приняты логические поля
DB-карточки и отдельная папка исходника/артефактов. История — в общем JSONL-журнале
с помесячной UTC-ротацией: `home/journal/YYYY-MM.jsonl` (§7/§12 M1-REQUESTS),
без индексации. Начальные 10 статусов приняты в §3.3/§11.
Справочник request_statuses(id, code, is_terminal) и FK requests.status_id → request_statuses.id
приняты (§18/§19): допустимые значения и терминальность — в БД, добавление без миграции схемы.
Переименование code не меняет карточки; при создании агент/инженер явно задаёт статус,
без is_initial/default, иначе ошибка (§20).
Для id всех четырёх таблиц принят INTEGER PRIMARY KEY (§21).
Типы/constraints, BEGIN IMMEDIATE-нумерация, путь БД и partial с явной сверкой
приняты в M1-START (§22 M1-REQUESTS). Id и number сохраняются оба.
Именование проектных запросов `CODE-number-english-slug` и нумерация приняты
в M1-REQUESTS §2.4/§15; дополнения — projects.code и requests.number, без копий ключа/slug/ветки.
Запросы без проекта разрешены (§16): project_id допускает NULL без фиктивного проекта;
ключи REQ-number, отдельная общая нумерация и home/requests/ приняты (§2.5/§17).
REQ зарезервирован, история остаётся scope=request, не global.
Полная JSONL-оболочка принята (§3.6/§14): обязательные at/scope/event_type/text,
необязательный artifacts с путями относительно home.
Обязательный event_type принят (§13): note/request_created/status_changed;
назначается CLI по операции, служит фильтрации, не запускает исполнение.
Scope global/org/project/request, поля type/key и правила фильтрации приняты
в §3.7/§10; статусы §3.3 дополнены research/planning/review/blocked/paused/failed
по прямому запросу инженера (§11), без обязательного pipeline. Исправленный целевой context root — `home/projects/<org>/<project>/`;
это не разрешение переноса legacy-данных.
[M1-STORAGE.md](docs/M1-STORAGE.md) отозван: DB-capture, универсальные operations
и recovery engine не закладываются заранее.

### Acceptance M1

- Все существующие полезные сценарии выполняются через Node.js без Python.
- Запрос инженера можно зафиксировать, прочитать и вести его статус/прогресс
  без запуска flow. Текущий статус — в БД; исходник/материалы — в папке задачи;
  append-only история — в общем JSONL-журнале. Выборки задачи/проекта/организации
  не теряют записи из-за ротации и не подмешивают чужой scope. Нет двух независимо редактируемых оригиналов
  или обязательной записи каждой команды в operations.
- Не теряется текст capture/note/journal; отсутствуют traversal, silent overwrite,
  lost update и side effects при чтении.
- Повтор импорта/восстановления не дублирует данные; повреждённый вход не
  заменяется пустым успешным состоянием.
- Локальный успех отличим от DB/git failure и от remote sync; непрошедший
  git commit не заставляет слепо повторять append.
- Восстановление из DB-backup действительно выполнено и проверены ссылки
  на контекстные артефакты. Git не объявляется backup всей системы.
- Модульные границы и направления импортов из [M1-DESIGN.md](docs/M1-DESIGN.md)
  проверяются механически; нет циклов, обхода публичных API или доменной логики в scripts.
- Обязательный `verify` по [TESTING.md](docs/TESTING.md) проходит в согласованном
  бюджете; проверены ограничения запуска, чувствительность критических checks
  и дополнительная ценность тестов. Одного fast-профиля недостаточно.
- Учёт запросов полезен без runner, flow, tracker и сети; обычная работа
  по-прежнему возможна без обязательного request.

## После M1 — направления, не обязательная очередь

По отдельному запросу и реальной задаче:

- Расширение учёта запросов под реальные требования flow/сабагентов;
  простой request/status/progress уже относится к M1.
- Юнит с подходящим input/output и собственной политикой приёмки.
- Композиция юнитов в flow; runtime фиксирует прогресс/результаты в БД.
- Проверка конкретного Pi runner, прав, отмены, isolation и recovery до запуска.
- Переиспользование юнитов, tracker, табы или multi-device — когда появится
  потребность, без обязательного предварительного marketplace/облака.

Ownership для нескольких устройств нужен до второго автономного writer,
не как следствие дерева процессов. Приёмка может быть автоматической, агентной
или человеческой по контракту юнита; новые внешние права от этого не появляются.
Точная state machine/DSL сейчас не утверждаются.

## Что не делать

- Не запускать реализацию по одному факту согласования архитектуры.
- Не оставлять Python под Node-обёрткой как новый backend.
- Не делать Markdown источником текущего управляемого состояния или DB-кэшем
  наоборот; текстовый журнал хода работы не подменяет DB-статус.
- Не синкать mutable DB через git и не обещать атомарность git+SQL.
- Не добавлять поля/таблицы/сервисы будущих flow до появления соответствующей задачи.
- Не навязывать request, tracker, reviewer или human approval любой обычной работе.
- Не переносить чужой command set целиком и не обещать непроверенные гарантии Pi.
