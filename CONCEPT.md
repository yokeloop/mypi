# Концепция mypi: синтез yokemate-pi и NorthStar

Статус: набросок концепции, фаза 1. Документ объясняет, **что откуда взято** и
**почему**, а не является инструкцией к немедленной реализации последующих фаз.

## Зачем

Yokemate-pi доказал механику личной памяти агента (home/-git, journal, knowledge,
warmup), но его поток завязан на tickets и оркестрацию разработки. NorthStar
спроектировал request-centered lifecycle с сильными инвариантами (explicit capture,
immutable artifacts, separation of roles), но пока не имеет живой memory-механики:
в репозитории только контракты, без runtime.

mypi — попытка взять лучшее из обоих, начав с минимума:

- из **yokemate-pi**: механику ведения памяти (структура, форматы, дисциплина записи);
- из **NorthStar**: продуктовые принципы (capture, инварианты, иммутабельность,
  глоссарии, путь к распределённости — но без преждевременного усложнения).

## Что взято из yokemate-pi

### 1. `home/` — вложенный git-репозиторий личных данных

Движок (mypi) в git не входит, `home/` имеет свой remote и синкается между
машинами как единое целое. Инстансы на разных машинах — равноправные пиры:
наблюдаемые факты едут через git, локальные пути могут отличаться.

**Почему:** единственный доказанный способ синка памяти между устройствами без
multi-master БД. Git уже решает идентичность, историю, версии и recovery.

### 2. Журнал — только исходы

`home/journal/YYYY-MM.md`, newest-first, один файл на месяц. Формат записи:

```markdown
## YYYY-MM-DD — <org>/<project> — <id или "no ticket">

- что реально сделано, по строке на исход
- решения и их «почему» в той же строке
- ссылки на артефакты по путям в home/knowledge/
```

Правила: реальные исходы, не процесс; записи для поиска (имена файлов/тикетов/функций);
тупик с потраченным временем — тоже исход; прошлые записи не переписываются;
несколько проектов в одной сессии → отдельная запись на каждый.

**Почему:** journal отвечает на «что мы делали и почему» месяцами позже —
это индекс, а не полная история. Артефакты лежат в knowledge по путям.

### 3. Knowledge per project

`home/knowledge/<org>/<project>/`:
- `context.md` — глоссарий домена: термины, которые пользователь и агенты
  обязаны понимать одинаково;
- `adr/` — решения с контекстом, статусами (proposed/accepted/superseded);
- `ai/<slug>/` — иммутабельные артефакты задач: plans, reports, research.
  Journal ссылается на них по пути, не пересказывая.

### 4. Warmup на старте сессии

Дайджест: хвост журнала, активные проекты из паспорта, inbox drafts. Это
проекция — индекс, не сама память. Вопросы вида «что было по X» → читать
полные записи и артефакты по путям, не пересказывать из дайджеста.

### 4а. MEMORY.md — общая память агента

`home/MEMORY.md` — плоский список стабильных фактов, договорённостей и
предпочтений, применимых к любой сессии. Подгружается первым блоком warmup
на старте каждой сессии.

Разделение с журналом: journal — исходы работы (что сделали и почему),
MEMORY.md — как работать (факты и правила, которые агент должен знать до
первого действия). Волатильное состояние сессии туда не пишется.

### 5. Паспорт проектов

`home/projects.json` — манифест известных проектов: org, name, локальный путь
клона, опционально tracker/model. Путь машинозависим — остальное переносимо.

## Что взято из NorthStar

### 1. Request, а не ticket, как корневая сущность

Главная сущность — request. Ticket (YouTrack/GitHub) — лишь один из source
artifacts request, никогда не обязательное условие начала работы. На фазе 1
request вырождается в draft-строку в `inbox.md`, но модель уже request-centered:
работа начинается с явного capture, а не с тикета.

**Почему:** старый ticket-driven поток слишком жёсткий — без тикета нельзя
начать. Capture сохраняет исходную мысль без изменений; оформление — отдельно.

### 2. Explicit capture

Обычное сообщение не создаёт сущность. Запись в inbox рождается только из
явного «capture». Draft хранит исходную формулировку без изменений (later
grooming отдельно), с готовностью к превращению в работу.

**Почему:** защита от захламления памяти случайно произнесёнными мыслями.
Capture — дешёвый, поэтому пользуются; enqueue — осознанный шаг.

### 2а. Путь draft → работа

Draft в inbox → (в фазах 2+) явный enqueue → работа. Даже на фазе 1 правило
одно: **capture дешёвый, начало работы — нет**. Начало работы над draft —
всегда осознанный шаг инженера.

### 2b. Иммутабельность артефактов и адресуемость

Все значимые артефакты (plans/reports/ADR) — файлы по стабильным путям с
датами/идентификаторами в имени, не переписываемые задним числом. Journal и
inbox ссылаются на них по пути. Артефакт, на который нельзя дать ссылку, не
существует.

**Почему:** NorthStar: «артефакт, на который нельзя дать ссылку, не существует».
Ссылки по путям + git = дешёвая provenance без хешей и object storage.

### 2c. Глоссарии как контракт общего языка

context.md и ADR в NorthStar — не «документация», а контракт: агент обязан
сверять термины с глоссарием до принятия решений. Трёхуровневая модель
(user glossary → project glossary → request terminology) на фазе 1 сжата до
project-level context.md; user-level появится при втором проекте, отличном
по домену.

### 3. Инварианты и дисциплина записи

Из lifecycle-контракта NorthStar взяты правила, применимые к памяти:

- Source request хранится в исходном виде; уточнения — отдельно от него.
- Пробелы фиксируются явно, не молчанием.
- Отделять facts / decisions / open questions / risks в рассуждениях.
- Терминальные записи не reopen-ятся: продолжение — новая связанная запись.

### 4. Отложено на фазы 2+

Из NorthStar **намеренно не берётся** на фазе 1:

- Оркестратор, сабагенты, табы/клоны чатов, sandbox, БД статусов, leases/ownership.
  NorthStar сам запрещает реализацию до принятия контрактов — mypi не обгоняет.
- Tracker-интеграции (YokeFlow) и command set старых систем.
- БД для статусов задач: на фазе 1 статуса нет — есть журнал исходов и inbox.
  Облачная БД из исходной идеи появится на фазе 3, когда появится что статустить.

**Почему:** фаза 1 должна быть полезной сама по себе без единого агента.
Сначала доказать, что память работает, потом строить вокруг неё workflow.

## Границы фазы 1

| Область | Фаза 1 (сейчас) | Фаза 2+ (потенциал) |
|---|---|---|
| Сущность работы | draft в inbox.md | request lifecycle Draft→…→Done |
| Память | home/-git: journal, knowledge, notes | + user glossary, request terminology |
| Статусы | нет (журнал исходов) | очередь в облачной БД (PostgreSQL, single authoritative store) |
| Синк | git-remote у home/ | то же + leases/outbox при многонодовой работе |
| Инструменты | python3-CLI (stdlib) | typed tools, agent runner |
| Проекты | projects.json (паспорт) | + tracker, models, cross-repo contracts |
| Оркестрация | нет | сабагенты, табы, playbooks |

## Открытые вопросы (не блокируют фазу 1)

1. User-level glossary: отдельный файл в home/ или context.md на уровне проекта?
2. Inbox: один файл или per-month? (фаза 1 — один, пересмотр при росте)
3. Паспорт: включать ли tracker/model в фазе 2 — пока избыточно.
4. Нужен ли SessionStart-хук Pi для warmup — решается при внедр.
5. Формат mypi.db — SQLite для локальной проекции (тёплый кэш) — фаза 2/3.
5b. Как связывать draft→request при переходе фаз (id? slug?) — до фазы 3.
5c. Схема облачной БД статусов — проектируется из опыта фаз 1-2, не заранее.

Открытые вопросы фиксируются здесь же, не в чате: чат — volatile, документы — durable.
