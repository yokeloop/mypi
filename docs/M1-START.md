## 1. Минимальная схема БД

Четыре предметные таблицы SQLite STRICT. Здесь зафиксированы поля, типы и ограничения; начальная исполняемая миграция создана в ходе M1 (M1-IMPLEMENTATION).

| Таблица | Поля |
|---|---|
| `organizations` | id, slug |
| `projects` | id, org_id, slug, code, checkout_path |
| `request_statuses` | id, code, is_terminal |
| `requests` | id, project_id, number, title, status_id, context_dir, created_at, updated_at |

### Типы и обязательность

- У каждой таблицы id — INTEGER PRIMARY KEY, выдаваемый SQLite. Выбор принят ранее в M1-REQUESTS §21.
- org_id, project_id, status_id и number — INTEGER.
- is_terminal — INTEGER с допустимыми значениями 0/1.
- Остальные поля — TEXT; created_at/updated_at записываются в едином формате UTC ISO 8601.
- NULL допустим только для requests.project_id и projects.checkout_path. Запрос может быть без проекта, проект — без рабочего клона; checkout_path хранит необходимую локальную привязку, а не идентичность проекта.
- Поля source_text/progress и копия публичного ключа в SQL не добавляются. Справочник статусов не содержит is_initial/default; статус при создании задаётся явно.

### Уникальность и ссылки

- organizations.slug уникален во всём хранилище.
- Пара projects(org_id, slug) уникальна; projects.code уникален глобально. Сохраняются принятые прописные латинские коды и резервирование REQ.
- request_statuses.code уникален; requests.context_dir уникален и остаётся путём относительно home с уже принятыми проверками безопасности.
- Для проектных запросов действует UNIQUE(project_id, number). Для непроектных — отдельный уникальный индекс по number WHERE project_id IS NULL; обычного ограничения с NULL недостаточно.
- projects.org_id → organizations.id; requests.project_id → projects.id; requests.status_id → request_statuses.id. Внешние ключи включены.
- Удаление связанных родителей запрещено: организация с проектами, проект с запросами и используемый статус не удаляются. Каскадов и ON DELETE SET NULL нет. Команды удаления организаций/проектов этим пакетом не вводятся.

### Нумерация и статусы

id и number сохраняются оба: id — внутренний ключ среди всех запросов, number — положительный номер в собственной последовательности проекта или в общей непроектной последовательности. Публичные CODE-number/REQ-number вычисляются по принятому контракту.

Следующий number определяется по сохранённым строкам своей последовательности, а вставка выполняется в той же BEGIN IMMEDIATE транзакции. Нет незащищённого MAX+1 между двумя командами или отдельной таблицы счётчиков. Сохранённые запросы не удаляются, их номера не переиспользуются; пропуски допустимы.

При создании CLI/API разрешает явно переданный code статуса через справочник и сохраняет его id. Переименование меняет только code статуса, не карточки запросов и не историю. Используемый статус нельзя удалить или изменить у него is_terminal; для иного поведения создаётся другой статус. Принятый начальный набор, значения состояний и запрет reopen терминальных запросов — в M1-REQUESTS §3.3.

## 2. Размещение БД

Принят путь:

```text
$XDG_STATE_HOME/mypi/state.sqlite3
```

Если XDG_STATE_HOME не задана:

```text
~/.local/state/mypi/state.sqlite3
```

БД и её служебные файлы находятся вне git контекста и движка. Контекст остаётся в `<mypi>/home/`; отдельное поле пути БД в конфиге не вводится. Разработка и тесты используют изолированные временные хранилища, не личные данные. БД и snapshots не хранятся в git; способ backup/restore уточняется до подключения реальных данных.

## 3. Частичные сбои и продолжение

SQL, файлы и Git не составляют одной транзакции. Ошибка незавершённой SQL-транзакции не отменяет её обычный rollback; уже подтверждённые изменения БД не откатываются автоматически ради имитации общего rollback при сбое файловой части или Git. Универсального recovery engine и operation records нет.

При частичном успехе CLI возвращает ненулевой exit code и результат partial:

- ID запроса, если карточка существует, и путь контекста;
- что подтверждённо сохранено;
- что осталось выполнить.

Агент продолжает после сверки БД, файлов, журнала и Git. Существующую карточку повторно не создаёт, исходник не перезаписывает, журнал вслепую повторно не дописывает. Через общий API завершаются только недостающие действия. При неудачной SQL-регистрации уже сохранённый исходник не удаляется.

Если точную историю потерянного перехода восстановить нельзя, её не выдумывают: фиксируют note о проверенном текущем состоянии. Повреждённые или неоднозначные данные означают остановку с диагностикой, а не автоматическое переписывание истории. Потерянный ответ требует сверки; exactly-once audit и автоматический retry/resume не обещаются.

Полный успех возвращается только после всех требуемых частей операции. В локальный git commit включаются только относящиеся к ней изменения. Принятые границы и последовательности сценариев уточнены в M1-REQUESTS §3.4.

## 4. Тестирование и граница старта

Стартовые рабочие цели и аварийные пределы приняты. Единственный нормативный источник чисел и правил запуска — [TESTING.md](TESTING.md), §6; запись принятия — §11. Лимиты не являются измеренным baseline; локальный механизм ограничения и его проверки описаны в M1-IMPLEMENTATION. Полная защита trusted gate/CI ещё не реализована. Без доступных ограничений suite не запускается неограниченно, собственный supervisor не создаётся.

Точные версии и совместимость Node 24/pnpm/TypeScript/better-sqlite3 проверяются технически при разрешённой настройке. Это не повод запрашивать отдельное согласование каждой версии при сохранении принятого стека. Импорт legacy и backup/restore уточняются до подключения реальных данных; они не блокируют начало разработки на временном хранилище. Прочие детали реализуемых команд определяются по принятому контракту, без проектирования будущих flow.

Принятие пакета не разрешает реализацию, установку зависимостей, миграцию данных, коммиты движка, работу с ветками или внешние записи. Такой запрос впоследствии получен («начинай»); ход реализации фиксируется в M1-IMPLEMENTATION. Границы миграции личных данных, коммитов и внешних записей сохраняются.
