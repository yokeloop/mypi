## REQUEST_CHANGES — для дизайна

Статическая проверка без инструментов. В publisher явного обхода не обнаружено, но в build-изоляции есть конкретная ошибка.

### 1. Изменяемый исполняемый файл пересекает границу sandbox → host

**Файлы:** `scripts/ci.sh`, `scripts/check.sh`.

В build-sandbox весь каталог подключён на запись:

```bash
--bind "$work" /work
```

Read-only overlays защищают перечисленные исходники, зависимости и скрипты, **но не `/work/tools/node`**. Следовательно, утверждение «Only generated output is writable» неверно.

После сборки этот же файл используется уже вне `bwrap`:

```bash
PATH="$work/tools:$PATH" bash scripts/check.sh verify
```

В начале `scripts/check.sh` выполняется:

```bash
node -p 'process.versions.node.split(".")[0]'
```

Таким образом, процесс внутри build-sandbox, получивший возможность исполнения произвольного кода, может заменить `/work/tools/node`; следующий этап запустит замену на хосте **до входа в bounded test unit**. Это также позволяет подменить дальнейшую проверку и получить успешный результат `verify`.

**Ограничение вывода:** предоставленные файлы не доказывают, что обычный TypeScript-вход способен выполнить код при сборке; `scripts/build.sh` здесь отсутствует. Это не доказанный сквозной эксплойт из PR, а конкретная ошибка границы изоляции: изменяемый sandbox-файл впоследствии исполняется доверенным хостом.

**Исправление без новых зависимостей и бюджетов:**
- минимум — подключить `$work/tools` отдельным read-only mount;
- предпочтительно — сделать workspace read-only, оставив writable только необходимые выходные каталоги, согласовав это с очисткой в `scripts/build.sh`;
- не исполнять на хосте инструменты, которые предшествующая sandbox могла изменить.

### Что в control plane выглядит корректно

**`.github/workflows/m1-verify.yml`:**
- Bootstrap push не вызывает publisher и правильно не считается trusted check.
- Для PR инструменты берутся из base, candidate находится отдельно; checkout не сохраняет credentials.
- Publisher работает на отдельном runner, не принимает candidate-артефакты и не исполняет PR-код.
- Принимая предоставленный readback environment как факт, разрешение только **branch `main`** исключает обычные PR merge refs и одноимённые tags.
- Только `needs.verify.result === 'success'` превращается в успешный App check; остальные результаты дают failure.
- Проверяются событие, точный workflow/ref и формат SHA; результат публикуется на head SHA.

**`docs/M1-PUBLISH.md`:**
- Отдельный App ID как источник required check закрывает подделку одноимённым GitHub Actions check — **после фактической настройки protection**.
- Bootstrap, отдельное согласование promotion и полномочия администратора описаны честно.
- Незавершённая регистрация App не выдается за готовую защиту.

### Runtime proof пока отсутствует

После исправления и отдельно одобренного promotion нужны подтверждения:
- доступности указанных версий Node/pnpm и работоспособности sandbox на выбранном runner;
- корректного успеха, failure и timeout с очисткой процессов;
- публикации check именно нужным App;
- невозможности удовлетворить protection одноимённым Actions check.

**Итог:** исправить writable-tool bridge. Регистрация App, установка ключа и включение protection остаются незавершённым rollout, а не уже доказанной защитой.
