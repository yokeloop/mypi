## Итог

**Есть два блокирующих замечания:** обход защиты опубликованных артефактов и возможность подменить обязательный CI-check. Поэтому diff пока нельзя принять только с оговоркой об отложенном rollout.

Обзор исключительно статический. **Сборку, тесты, GitHub job и настройки protection я не проверял исполнением.**

## Перепроверка предыдущих замечаний

1. **Dangling symlink — исправлено для описанного сценария.**  
   В `src/infrastructure/filesystem/paths.ts` отсутствующий путь теперь проверяется через `lstatSync`, символическая ссылка отклоняется. В `test/fast/paths-cli.test.ts` есть отрицательный пример и положительный контроль обычного отсутствующего файла.

2. **Подмена опубликованного артефакта — прямой сценарий исправлен, инвариант закрыт не полностью.**  
   `progress`, `complete` и `restoreContext` используют множество опубликованных путей; сравнение с Git blob защищает уже закоммиченный артефакт. Тест проверяет отказ повторной публикации, отсутствие новой записи и допустимость новой версии. Однако источник множества опубликованных путей сам недоверенный — подробности ниже.

3. **Журналирование переименования — исправлено.**  
   `src/app/request-work.ts` отдельно формирует изменение title и переход статуса. Boundary-тест проверяет тип `note`, прежний/новый заголовок, причину и неизменность статуса/папки. Дополнительная проверка отсутствия `→` полезна, но не обязательна для принятия этой правки.

4. **Коллизии legacy-import — исправлено.**  
   План проверяется до регистрации проектов и копирования: дубли destination, конфликт с receipt и пересечение файл/каталог отклоняются. Тест содержит варианты с разными и одинаковыми байтами, проверяет отсутствие зарегистрированных проектов и receipt.

Также устранены прежние слабости:
- идемпотентность Git теперь сравнивается с правильным SHA;
- `verifyReferences` вызывается непосредственно после удаления артефакта;
- IPC-тест действительно удерживает первого writer внутри source callback до INSERT; второй обязан получить отказ **до своего callback**;
- основная CLI-матрица перенесена в in-process dispatch, процессы оставлены для отдельных интеграционных границ;
- journal FS-тест не создаёт ненужную SQLite fixture. Его сохранение в boundary обосновано заявленным ограничением permission-mode на `fsync`; повторного переноса в fast не требую.

## Блокирующие находки

### 1. P1 — защита артефакта зависит от редактируемого журнала, а не от сохранённой публикации

**Файлы:**
- `src/app/create-workspace.ts` — `core.serialize`;
- `src/modules/knowledge/public.ts` — `publishedArtifacts`;
- `src/infrastructure/git/context-git.ts` — `validate`, `commit`.

`published` вычисляется исключительно из текущего рабочего JSONL. Перед использованием этого множества не проверяется, что сохранённые в Git записи журнала не удалены или не переписаны.

**Воспроизводимый по коду сценарий:**

1. Успешно опубликовать `artifacts/proof.md` через `progress`.
2. В рабочем JSONL удалить поле `artifacts` у ссылающейся записи, сохранив валидную оболочку.
3. Изменить байты `proof.md`.
4. Вызвать `app.complete([путь_артефакта], message)`.
5. Вернуть рабочий JSONL к исходным байтам.

На шаге 4 `journal.published()` уже не содержит путь. Обычный артефакт не подпадает под остальные категории immutable/append-only, поэтому `validate` пропускает замену. `commit --only` коммитит артефакт, не включая изменённый журнал. После шага 5 рабочее дерево снова может быть чистым, но старая журнальная ссылка предъявляет новые байты.

Это не требует переписывания Git-истории или прямого изменения БД. Проверка запрета переписывать журнал не помогает: журнал вообще не передавался в `complete`.

**Минимальное исправление:** множество защищённых путей должно включать публикации из доверенного committed-состояния журнала, а не только из worktree. Например, объединять ссылки из HEAD и текущего журнала. Другой вариант — до использования worktree-журнала проверять сохранность committed-префиксов всех журнальных файлов, включая обнаружение удалённых файлов. Проверки только переданных в `commit` путей недостаточно.

**Узкий regression-тест:** расширить существующий `test/boundary/requests.test.ts`:
- сохранить исходный JSONL и HEAD после публикации;
- убрать ссылку из рабочего журнала и изменить артефакт;
- потребовать отказ `complete([artifact])` и неизменность HEAD;
- восстановить журнал;
- сохранить положительный контроль новой версии артефакта.

Дополнительные CLI-процессы не нужны.

### 2. P1 — required check привязан к имени и GitHub Actions, но не к доверенному workflow

**Файлы:**
- `.github/workflows/m1-verify.yml`;
- `scripts/ci.sh`;
- `docs/M1-CI.md`.

Для штатного `pull_request_target` разделение base/candidate выглядит правильным: PR не выбирает исполняемый checker, candidate-зависимости не устанавливаются, его код запускается внутри ограниченной среды.

Но обязательный check, согласно описанию protection, идентифицируется как `trusted-verify` от приложения GitHub Actions. Это **не идентичность конкретного доверенного workflow**.

В представленном workflow есть особенно прямой путь обхода: `workflow_dispatch` допускает выбранный ref. После публикации workflow в main пользователь с достаточными обычными правами записи/запуска Actions может:

1. создать ветку с изменённым workflow или `scripts/ci.sh`;
2. запустить workflow вручную на этой ветке;
3. получить успешный check с именем `trusted-verify` на SHA этой ветки.

При dispatch оба checkout используют `github.sha`: «base» и candidate являются разными каталогами **одной выбранной ревизии**. Проверка `base != candidate` этого не предотвращает; policy-сравнение также не обнаружит самоподмену.

Более общий вариант — другой workflow с тем же именем job/check. Он тоже публикуется приложением GitHub Actions. CODEOWNERS требует review при слиянии, но сам по себе не запрещает выполнение workflow из ещё не принятой ветки.

**Это отдельная проблема, не заявленная административная граница.** Для такого сценария не требуется менять branch protection административными credentials.

**Минимальное исправление зависит от доступных средств GitHub:**
- обязательная проверка должна быть привязана внешним правилом к конкретному доверенному workflow/ref, если используемый ruleset это поддерживает; либо
- результат должен публиковать отдельный доверенный проверяющий субъект, чьи credentials недоступны branch workflows.

Ограничение dispatch на main полезно, но условие внутри изменяемого branch-workflow **само по себе не закрывает подмену одноимённого check**. Удаление одного `workflow_dispatch` также не решает общий случай.

**Узкая проверка после настройки:** в одноразовой ветке попытаться получить одноимённый зелёный check через недоверенный workflow/dispatch и убедиться, что он **не удовлетворяет** обязательному требованию. Отдельно показать, что настоящий trusted verifier удовлетворяет его именно для проверенного head SHA. Это проверка control plane, не новый продуктовый тест и не попытка ресурсного истощения.

## Необязательные рекомендации

- В IPC-тестах `test/boundary/contention.test.ts` и abrupt-exit сценарии добавить небольшой явный deadline ожидания checkpoint и гарантированное ожидание завершения ребёнка при аварийном выходе теста. Общий systemd deadline уже ограничивает ущерб; рекомендация касается скорости диагностики, а не отсутствия внешнего ограничения.
- Постепенно усилить существующую parser-матрицу точными ожидаемыми `name`, `args`, `options`. Сейчас одна подробная строка и in-process dispatch существенно лучше прежнего покрытия, но проверка только `type` для остальных строк остаётся слабой.
- Не расширять lifecycle-тесты дополнительными subprocess-матрицами. Для обеих продуктовых проверок выше достаточно существующих API boundary fixtures.

## Отдельная оценка CI readiness

**CI ещё не готов к признанию обязательным доверенным gate.**

Положительные свойства проекта: pinned Actions, read-only token, отсутствие сохранённых checkout credentials, установка зависимостей только из base, изолированная сборка и повторное использование bounded `verify`.

Однако сначала необходимо устранить подмену check. Затем нужны контролируемая публикация reviewed base и настоящий hosted-прогон, подтверждающий работу Ubuntu/AppArmor/user-systemd/cgroup и привязку результата к проверяемому SHA.

Отсутствие workflow в текущем main, необходимость административного bootstrap и возможность администратора изменить protection честно обозначены как rollout-ограничения. Я не считаю их доказательством ни работающего CI, ни дефекта продуктового кода. Локально заявленный прогон также не выдаю за проверенную hosted-готовность.

**Код и тесты:** существенное улучшение, но замечание №1 блокирует принятие.  
**CI:** разумный проект изоляции, но замечание №2 блокирует принятие модели trusted check.
