## Продукт: REQUEST_CHANGES

Статическое ревью предоставленных фрагментов; код и тесты не запускал.

**Основной обход через подмену журнала закрыт:** `validateJournal()` перечисляет пути из Git HEAD, а не из рабочей директории. Поэтому удаление отслеживаемого журнала также обнаруживается. Проверка размера и хеша префикса запрещает изменение прежних байтов, сохраняя возможность дописывания. Для операций через `core.serialize()` эта проверка предшествует `journal.published()`. Импорт также вызывает её до изменения данных.

### Остался обход заявленного общего барьера валидации

**Файл:** `src/app/create-workspace.ts`

Обёртка `core.serialize()` не перехватывает все мутации возвращаемого workspace:

```ts
projects: core.projects
```

и:

```ts
addStatus: core.requests.addStatus,
renameStatus: core.requests.renameStatus,
setTerminal: core.requests.setTerminal,
removeStatus: core.requests.removeStatus,
```

Это исходные методы `database`: создание объекта через spread и замена свойства `serialize` не перенаправляют внутренние вызовы и замыкания этих методов на новую обёртку.

**Конкретный сценарий:**

1. Иметь журнал, уже сохранённый в HEAD.
2. Удалить его либо переписать существующую запись.
3. Вызвать корректный `app.projects.add(...)` или `app.statuses.addStatus(...)`.

Эти публичные маршруты не проходят через показанную проверку журнала и могут изменить БД при повреждённой истории. Это не доказательство возможности закоммитить изменённый опубликованный артефакт, но конкретный обход заявленного условия «каждая мутирующая workspace-транзакция сначала проверяет журналы».

**Необходимое исправление:** провести существующие публичные мутации проектов и статусов через тот же проверяемый транзакционный вход. Добавить регрессионные проверки: изменение и удаление журнала из HEAD должны блокировать эти операции, оставляя **БД и HEAD** неизменными. Новые возможности продукта для этого не нужны.

Предоставленный тест с подменённым журналом и изменённым артефактом проверяет правильный сценарий, но вызывает `complete()`, который уже использует обёртку, поэтому этот пропуск не обнаруживает.
