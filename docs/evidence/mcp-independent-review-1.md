## Текущие дефекты

### 1. **P1 — потеря CLI scope с успешной записью в global**
**Пути:** `src/cli/app-command.ts:14`, `src/app/resolve-scope.ts:10,21–23`.

Новый перевод объединяет отсутствующий scope, пустую строку и строку `global`. До изменения контекстные команды передавали scope непосредственно в `projects.resolveScope`: `global` мог быть именем зарегистрированной организации, а пустая строка отклонялась.

**Repro на временной установке:**
1. Зарегистрировать `global/project`.
2. Выполнить `memory add "org-only" -s global`.
3. Вместо `home/projects/global/MEMORY.md` изменяется `home/MEMORY.md`, команда сообщает успех.

Также `memory add "fact" --scope ""` теперь успешно пишет глобально вместо ошибки. Затронуты `note`, `memory show/remove`, `warmup`: возможны запись/удаление не на том уровне и раскрытие глобального inbox через warmup.

**Исправление:** различать отсутствие аргумента и явно переданное значение; сохранить прежнюю семантику контекстного CLI отдельно от journal-синтаксиса. Глобальный default можно передавать объектом `{type:"global"}`.

### 2. **P2 — ошибки валидации обходят объявленный structured error-контракт**
**Путь:** `src/mcp/server.ts:16–22`.

SDK валидирует `inputSchema` **до** callback. Его обработчик ошибок возвращает только `isError` и текст, без `structuredContent`; `failure()` здесь не вызывается. Аналогично обрабатывается неизвестный инструмент.

**Repro:** `tools/call` для `memory_add` с `{text:"x"}`:
- `isError:true`;
- отсутствует `{status:"error", message:…}` в `structuredContent`;
- `content[0].text` — диагностическая строка, не JSON того же результата.

Это нарушает заявленный единый формат ошибок и ломает потребителя, читающего ошибки через `structuredContent.status`. `test/boundary/mcp.test.ts:47–48` проверяет только `isError` и пропускает нарушение.

## Review тестового diff

- **Oracle:** независимые 31 примера — хороший контроль отсутствующих инструментов; expected не выводится из production registry. Partial проверяется по конкретным recovery-полям и устойчивому состоянию.
- **Cheapest level:** parser/schema/queue и checkout lookup проверяются правильно внутри процесса. Настоящий stdio-canary нужен, заменять mock нельзя.
- **Сохранность защиты:** прежние assertions `workspace-cli` сохранены; удалений scope-проверок ради green не обнаружил.
- **Пробелы:** отсутствуют случаи явного пустого scope и организации `global`; нет проверки structured-ошибки на протокольной границе.
- **Cancellation/shutdown:** fast доказывает отмену ожидающего вызова, но `stop()` проверяется после опустошения очереди. EOF/SIGTERM проверяются только без активной операции. Межпроцессный сценарий использует `Promise.all`, но не гарантирует фактического перекрытия writers.
- **Чувствительность:** в `docs/MCP-CYCLE.md` она оставлена следующим шагом; доказанных mutation/red→green результатов здесь нет.
- **Стоимость:** записанный одиночный verify укладывается в бюджет. Он не доказывает прирост относительно base или разброс стоимости. Полный lifecycle через MCP частично повторяет прежний boundary; сокращение возможно, но узкую реальную границу нужно сохранить.
