## Итог

**Нужны изменения:** обнаружены четыре конкретных дефекта, включая обход ограничения размещения БД и возможность подменить уже опубликованный артефакт.

Проверка исключительно статическая, по предоставленным исходникам и тестам. **Сборку и тесты я не запускал.** Заявления автора о полноте реализации не использованы как доказательства. CI в этот обзор не включён.

## Подтверждённые статические находки

### 1. P1 — dangling symlink обходит проверку внешнего расположения БД

**Файл / функции:** `src/infrastructure/filesystem/paths.ts` — `canonicalFuturePath`, `externalDatabasePath`.

**Причина:** `canonicalFuturePath` ищет существующего предка через `existsSync`. Для символической ссылки с отсутствующей целью `existsSync` возвращает `false`. Ссылка попадает в обычный строковый `suffix`, после чего результат уже не канонизируется.

**Сценарий:**

1. Снаружи репозитория существует `state.sqlite3`, являющийся ссылкой на ещё отсутствующий `engine/private.sqlite3`.
2. Проверка считает внешний путь допустимым и возвращает его, не обнаружив назначение внутри движка.
3. Этот путь передаётся открытию SQLite.

Сам **пропуск запрещённого назначения проверкой подтверждается кодом**. Последующее создание файла через конкретную сборку SQLite требует runtime-проверки; здесь оно не проверялось.

**Узкий regression-тест:** в `test/fast/paths-cli.test.ts` создать dangling symlink на отсутствующий файл внутри временного engine. Проверить отказ `externalDatabasePath` до открытия БД и отсутствие файла назначения. Положительный контроль — обычный отсутствующий файл снаружи engine должен разрешаться. Процессы не нужны.

### 2. P1 — опубликованный артефакт можно заменить под прежней журнальной ссылкой

**Файлы / функции:**

- `src/app/request-work.ts` — `progress`;
- `src/infrastructure/git/context-git.ts` — `commit`;
- `src/app/create-workspace.ts` — `complete`.

**Причина:** для уже существующего артефакта `progress` проверяет только `files.isFile`. Git-защита неизменяемости распространяется на `source.md`, inbox и append-only файлы, но не на материалы, ранее опубликованные через `entry.artifacts`.

**Сценарий:**

1. `progress` сохраняет `artifacts/proof.md` и публикует ссылку на него в журнале.
2. Файл редактируется вручную.
3. Следующий `progress` с `{ path: 'artifacts/proof.md' }` либо `context commit` успешно коммитит замену.
4. Старая запись журнала по тому же пути теперь предъявляет другое содержимое.

Git сохраняет старый blob, но журнальная ссылка не содержит revision, а API не отличает опубликованный артефакт от редактируемого рабочего материала. Это противоречит предоставленному контракту: следующая редакция опубликованного доказательства должна быть новым артефактом/версией, а не подменой.

**Узкий regression-тест:** boundary-тест с настоящим Git: опубликовать один артефакт, изменить его байты, попытаться повторно опубликовать тот же путь. Проверить отказ, сохранность прежнего committed blob и отсутствие успешного коммита замены. Новый путь версии должен приниматься. Не требуется повторять полный request lifecycle или запускать CLI.

### 3. P2 — переименование запроса журналируется как фиктивная смена статуса на самого себя

**Файл / функция:** `src/app/request-work.ts` — `change`.

Текст всегда строится так:

```ts
result.before.status + ' → ' + result.after.status + '. ' + reason
```

При изменении только title выбирается правильный `event_type: 'note'`, но содержание остаётся, например:

```text
planning → planning. clarification
```

**Сценарий:** пользователь меняет `Old title` на `New title`. БД успешно обновляется, однако журнал не сообщает ни факт переименования, ни старое/новое название. Контракт прямо предусматривает краткую запись о переименовании; сейчас вместо неё записывается вводящий в заблуждение текст.

`test/boundary/workspace-cli.test.ts` вызывает `request title`, но содержимое соответствующей записи не проверяет.

**Узкий regression-тест:** создать запрос, изменить только title и проверить новую запись: тип `note`, отражено переименование и его причина, отсутствует сообщение о переходе статуса. Дополнительно проверить неизменность `contextDir` и статуса. Лучше API-тест, без нового CLI-процесса.

### 4. P2 — план legacy-импорта допускает столкновения путей после преобразования

**Файл / функция:** `src/app/import-legacy.ts` — `importLegacy`, построение `plan`.

**Причина:** проверяются конфликты с уже существующим target, но не уникальность `destination` внутри самого плана.

**Сценарий:** архив содержит одновременно:

```text
one/project/journal/2026-09.md
one/project/legacy-journal/2026-09.md
```

Для обоих получается:

```text
projects/one/project/legacy-journal/2026-09.md
```

- При разных байтах сначала подтверждаются изменения БД и копируется один файл, затем возникает предсказуемый конфликт и возвращается partial.
- При одинаковых байтах импорт завершается успешно, хотя два разных исходных пути молча схлопываются в один.

Это не авария диска или конкурентное изменение: неоднозначность полностью известна до первого эффекта и должна быть диагностирована при построении плана.

**Узкий regression-тест:** маленький архив с двумя указанными путями и различным содержимым. Проверить отказ до регистрации проектов, создания receipt и копирования файлов. Для одинаковых байтов также проверить отсутствие молчаливого схлопывания. CLI-процессы не нужны.

## Оценка тестов

### Oracle: сильные стороны

В наборе есть содержательные, независимые проверки результата:

- точное сохранение Unicode/CRLF/BOM;
- SQL constraints на реальном SQLite;
- отсутствие изменения байтов БД при чтении;
- сохранность постороннего staged-файла;
- конкретные `PartialError.saved`, сохранённый исходник после SQL-ошибки;
- восстановление реальных данных из SQLite snapshot и Git bundle;
- отдельный abrupt-exit сценарий с checkpoint, а не только обычное исключение.

Это существенно сильнее проверок «exit 0» или наличия файла.

### Oracle: конкретные слабости

1. **Ложная проверка идемпотентности Git.**  
   В `test/boundary/context.test.ts`:

   ```ts
   assert.notEqual(history.commit(['notes/new.md'], 'idempotent completion'), first);
   ```

   `first` относится к более раннему коммиту `source.md`. Проверка пройдёт и при создании лишнего коммита на каждый повтор. Нужно сохранить SHA первого коммита `notes/new.md` и сравнить повтор именно с ним.

2. **Проверка отсутствующего артефакта останавливается раньше нужной проверки.**  
   В `test/boundary/maintenance.test.ts` файл удаляется, затем ожидается `/Dirty/`. Это доказывает запрет dirty backup, но **не** проверку битой журнальной ссылки в `verifyReferences`. Для этой ветки нужен чистый Git с удалённым обычным артефактом и оставшейся ссылкой в журнале.

3. **Параллельный тест не гарантирует пересечение критических участков.**  
   В `test/boundary/requests.test.ts` два `spawn` запускаются рядом, но могут фактически пройти последовательно. Oracle `[1, 2]` полезен, однако сам по себе слабо чувствителен к удалению защиты от гонки. Это ограничение доказательства, не подтверждённый дефект текущей нумерации.

4. **Парсер часто проверяется только по `type`.**  
   Матрица в `test/fast/paths-cli.test.ts` для workspace-команд почти везде утверждает лишь `type === 'workspace'`. Ошибка `name`, позиционных аргументов или передачи options может остаться незамеченной. Стоит усилить ожидаемые результаты существующих строк, а не размножать subprocess-тесты.

### Уровень

- Реальный SQLite в fast оправдан: проверяются именно SQL semantics, а не имитация хранилища.
- Реальные Git, launcher, restart и kill-сценарии правильно находятся в boundary.
- `test/boundary/journal.test.ts` использует только локальную FS, SQLite fixture и in-process API; Git и процессы ему не нужны. По представленным правилам это кандидат в fast. Более того, helper `state(t)` инициализирует БД, которая этому тесту не нужна.
- Значительная часть правил requests проверяется только внутри большого Git-сценария. Для локальных правил статусов/title это дороже необходимого; полноценную матрицу не следует дополнительно дублировать на CLI.

### Стоимость и ненужное дублирование

`test/boundary/workspace-cli.test.ts` запускает десятки Node-процессов, а изменяющие команды порождают ещё множество Git-процессов. Он повторяет существенные части request lifecycle, partial repair и backup/restore, уже проверенные напрямую в других boundary-файлах.

Дополнительная ценность launcher и нескольких сквозных связок реальна. Но проверка **каждой** команды отдельным процессом не обязательна для доказательства dispatch: значительную часть можно проверять через `run`/`executeCommand`, сохранив узкие process-canary для stdout/stderr, exit code, перезапуска и пути установки. Это соответствует предоставленной политике тестирования.

Сами ограничения времени не доказывают приемлемую стоимость. Без запусков я не могу подтвердить бюджеты 5/30 секунд, разброс, peak memory/tasks или назвать фактически самый дорогой тест.

## Гипотезы и оставшиеся неизвестные

- **Гипотеза о нестабильности при нагрузке:** SQLite ждёт блокировку до 1 секунды, при этом некоторые транзакции держат её во время нескольких Git-вызовов с отдельными timeout по 3 секунды. Параллельный boundary-тест может зависеть от скорости среды. Фактического отказа не наблюдал; это не отдельный подтверждённый product bug.
- Не проверены runtime-совместимость native-драйвера, фактический результат сборки и поведение Git установленной версии.
- Нет доказательства чувствительности тестов к конкретным мутациям. Приведённые выше regression-тесты — рекомендации, а не выполненные red→green проверки.
- Предоставленный контракт requests обрывается внутри §3.6; выводы не опираются на недоступное продолжение или отсутствующие документы по ссылкам.
- CI и полнота его защит намеренно оставлены отдельному обзору.
