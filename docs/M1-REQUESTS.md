## 1. Принятая граница

В управление проектами M1 входит явный учёт запросов инженера, их статусов и прогресса. SQLite — авторитетное управляемое состояние; исходник хранится в папке задачи, а история прогресса — в общем JSONL-журнале, не в SQL-полях source_text/progress.

Предметная основа БД: **`organizations`, `projects`, `requests`, `request_statuses`**. Последняя таблица — справочник допустимых статусов запросов, а не workflow engine (§18). Запрос/задача здесь — одна сущность `request`, не две таблицы и не обязательная цепочка преобразований.

- Фиксация запроса не запускает исполнение. Flow, сабагенты, runner и правила их исполнения остаются за пределами M1.
- Обычная работа по-прежнему возможна без учёта; не каждое сообщение становится request.
- MEMORY, журнал исходов, заметки и артефакты остаются файловым контекстом. Оперативный статус учитываемого запроса находится в БД, не в параллельно редактируемом Markdown.
- Отдельные `captures`, `operations`, `operation_files` не входят в эту основу. Capture не является обязательной ступенью перед request; legacy-inbox не превращается автоматически в список задач. Его формат не меняется в этой сессии.
- Не строим универсальный recovery engine, журнал каждой технической команды или историю всех переходов на будущее. Прежнее [предложение хранения](https://github.com/yokeloop/mypi/blob/580942ddce9dc907e683e27a45e114c3d2313f96/docs/M1-STORAGE.md) отозвано как преждевременное усложнение.

## 2. Принятая основа: DB-карточка и папка контекста

Одна задача = одна строка `requests` + одна каноническая папка исходника/артефактов + относящиеся к задаче записи общего журнала. БД отвечает «что это, чей запрос и в каком он состоянии», папка — «что просили и какие материалы подготовлены», журнал — «что произошло». Это разные данные, не редактируемые копии одного состояния.

### 2.1. Поля requests

| Поле | Смысл и обновление |
|---|---|
| `id` | Устойчивый внутренний ID записи; не зависит от заголовка, статуса или flow. Для проектных запросов публичный ключ CODE-number вычисляется по §2.4/§15; ключ без проекта — REQ-number (§2.5/§17). Принят INTEGER PRIMARY KEY (§21) |
| `project_id` | Необязательная связь с проектом, NULL для запроса без проекта (§16); INTEGER FK на projects.id (§22) |
| `number` | Для проектных запросов — положительный номер с 1, выдаётся БД в транзакции, уникален в паре с project_id (§15). Для запросов без проекта — отдельная общая последовательность с 1, уникальная среди запросов с project_id=NULL (§2.5/§17) |
| `title` | Короткий заголовок, предложенный ведущим LLM-агентом; редактируется явно, не заменяет исходник |
| `status_id` | Текущее состояние работы, внешний ключ на устойчивый request_statuses.id (§19); CLI разрешает явно заданный при создании code через справочник (§20). Меняется через API, не парсится из Markdown; допустимость и терминальность берутся из БД |
| `context_dir` | Единственная ссылка на каноническую папку контекста, относительно home |
| `created_at` | Время регистрации; назначает CLI/core, не LLM |
| `updated_at` | Время последнего успешно зафиксированного изменения карточки или progress через API |

В сценариях ниже status означает логическое состояние; в карточке хранится только status_id, отдельной копии code/status нет (§19).

`source_text` и `progress` **не входят в SQL-карточку**. Нет отдельного пути на каждый документ, percentages, flow-конфига или универсального JSON «для расширяемости». Запросы без проекта разрешены (§16); принятые типы/ограничения всех четырёх таблиц — M1-START §1 (§22).

Заголовок генерирует уже работающий агент и передаёт обычной строкой. Сам CLI не вызывает LLM и не требует настройки модели. Инженер тоже может задать/исправить title. Переименование title не меняет ID и папку.

`context_dir` хранится как явная относительная ссылка на ресурс, не как произвольная настройка пользователя. Для проектного запроса принятое имя папки — код проекта, номер задачи и английский slug (§2.4/§15); для запроса без проекта — REQ-number-english-slug внутри home/requests/ (§2.5/§17). Альтернатива с вычисляемым путём рассмотрена, но выбрана явная ссылка: расположение контекста не должно быть зашито в потребителей API.

Путь ведёт внутрь контекстного root, а при наличии проекта — внутрь его контекста; абсолютный путь, traversal и symlink-выход запрещены. Нормальный API не меняет project/context_dir при переименовании задачи. Не создаём сейчас команду переноса папок на будущее.

### 2.2. Контекст задачи

Принятый layout-ориентир для проектной задачи с именованием по §2.4/§15; не обязательный набор пустых каталогов:

```text
home/projects/<org>/<project>/requests/<CODE>-<number>-<english-slug>/
  source.md                 # исходная формулировка, без переписывания
  context.md                # при необходимости: актуальные уточнения и краткий обзор
  plans/                    # планы по мере появления
  research/                 # исследования по мере появления
  artifacts/                # остальные материалы задачи
```

Здесь `home/` — вложенное git-хранилище mypi, не системный `/home` Linux. `home/projects/` хранит контекст; рабочие клоны в `<mypi>/projects/` — другой каталог. Префикс projects не становится частью логического scope `org/project`. Например, context_dir хранит `projects/prineycom/mypi/requests/MP-23-add-jsonl-journal/`, без home и без ведущего `/`. Исправление layout не разрешает перенос legacy-данных.

При создании в папке достаточно `source.md`; запись о регистрации идёт в общий журнал. Остальные документы/каталоги появляются только с содержимым. Ни journal.md, ни journal.jsonl внутри задачи не создаются. Папка больше не обещает содержать полную историю работы. Все её пути принадлежат задаче, не выбранному flow; код рабочих проектов по-прежнему живёт в checkout, не копируется сюда.

- `source.md` сохраняет полученный исходный текст без trim, нормализации переносов и сгенерированной шапки. Новые уточнения не переписывают исходник: они попадают в context/артефакты и журнал. Уже сохранённый большой файл лучше принять файлом, а не гонять через аргумент shell.
- Общий append-only JSONL-журнал хранит хронологию значимых изменений, решений, результатов и тупиков. Прежние записи не редактируются; исправление — новая запись. Это человеческая история в структурированном формате, не state machine или источник текущего SQL-статуса.
- `context.md` — необязательный живой обзор: уточнённая задача, ограничения, ссылки на нужные материалы. Он не заменяет источник и журнал, не содержит второй авторитетный status/frontmatter.
- Рабочие планы/исследования могут редактироваться с git-историей. Опубликованные/принятые артефакты сохраняют адресуемую версию; следующая редакция — новый артефакт/версия, не тихая подмена доказательства.
- История задачи/проекта/организации получается фильтрацией общего журнала, а не копированием событий в несколько файлов по scope. Существующие legacy Markdown-журналы и errors не удаляются и не мигрируются этим решением; сводные контекстные заметки не становятся второй канонической историей запросов.

### 2.3. Размер текста и чтение

У SQLite TEXT нет обычного ограничения вида VARCHAR(255), хотя существуют лимиты движка/сборки, записи, памяти и ввода. Поэтому Markdown выбран **из-за роли контекста**, не потому, что SQLite не может хранить длинную строку.

Файлы тоже не бесконечны: ошибки размера, кодировки или диска сообщаются явно; source не обрезается для попадания в лимит. Хранение полного исходника и помещение его в контекст LLM — разные задачи. Список запросов читает небольшую DB-карточку, а агент открывает нужные документы/части большого файла по путям. Сводка не заменяет оригинал. Ограничение длины preview не изменяет сохранённый title/source. Численные лимиты ввода пока не назначаются без реальной необходимости.

### 2.4. Принятые именование и нумерация

Для проектных запросов приняты буквенный код проекта и инкремент номера внутри проекта; полное имя папки/ветки — `MP-23-task-name-example` (подтверждение §15). Это правило формы имени, не регистрация проекта с кодом MP и не разрешение создавать ветки.

Принятые правила:

- `projects.code`: прописные латинские буквы, например MP/YM/AAI; уникален среди всех проектов этого локального хранилища, независимо от org. Код REQ зарезервирован для непроектных запросов и проектам не выдаётся (§17). `org/project` остаётся проектной identity/scope; code — короткий публичный код, не имя каталога организации.
- Номер задачи — положительное целое с 1, отдельная последовательность на каждый проект. Поле `requests.number` и уникальность `(project_id, number)` приняты как минимальное дополнение к карточке. Номер выдаёт БД в транзакции регистрации, не LLM, сканирование папок или JSONL.
- Номера сохранённых задач не переиспользуются; в том числе сохраняются строки с терминальными done/failed/cancelled. Пропуски допустимы, бездырочная последовательность не обещается. Принято вычисление следующего номера по сохранённым запросам своей последовательности и вставка в той же BEGIN IMMEDIATE транзакции (§22). Незащищённого MAX+1 в двух отдельных командах нет; отдельный сервис/таблица счётчиков не нужны.
- Короткий публичный ключ — `MP-23`, вычисляется из code + number; отдельное поле с его копией не требуется. `id` остаётся внутренним ключом БД типа INTEGER PRIMARY KEY (§21); CLI и журнал используют публичный ключ. Дополнительный UUID не нужен.
- Код проекта фиксируется после появления задач; его смену с миграцией старых ссылок в M1 не добавляем. Перепривязка существующей задачи к другому проекту не часть обычного rename.
- Полное имя — `MP-23-add-jsonl-journal`. Slug — короткая смысловая фраза на английском, lowercase kebab-case: `[a-z0-9]+(?:-[a-z0-9]+)*`. Его предлагает ведущий агент; CLI проверяет форму и не вызывает LLM. `title` может оставаться на языке инженера, это не обязательно тот же текст.
- Slug выбирается при создании и входит в сохранённый `context_dir`. Исправление title не переименовывает папку/ветку автоматически. Отдельный SQL-столбец slug сейчас не нужен: полное имя уже содержится в context_dir.
- Когда создание рабочей ветки отдельно разрешено, её предложенное имя — то же полное имя задачи. Регистрация request сама не создаёт/не переключает ветку, не меняет рабочий checkout и не требует branch-поля в БД.

Пример, не реальные записи/ветки:

```text
project: prineycom/mypi, code: MP
request key: MP-23
title: Добавить общий JSONL-журнал
folder: home/projects/prineycom/mypi/requests/MP-23-add-jsonl-journal/
branch (если отдельно разрешена): MP-23-add-jsonl-journal
```

### 2.5. Запросы без проекта

Запросы без проекта **разрешены** (§16): project_id может быть NULL, фиктивный проект для регистрации не требуется. Это та же сущность request с принятой карточкой, статусами, исходником, материалами и историей, не новый capture/inbox и не автоматическое исполнение. Правила §2.4 о коде проекта и его последовательности относятся к проектным запросам.

Именование, нумерация и размещение непроектных запросов **приняты** (§17):

- Короткий ключ — REQ-1, REQ-2 и далее; REQ резервируется для непроектных запросов и не выдаётся проектам как projects.code.
- Одна общая последовательность requests.number с 1 для запросов без проекта, выдача БД в транзакции, без переиспользования сохранённых номеров; пропуски допустимы.
- Папка — `home/requests/REQ-1-short-slug/`, context_dir — `requests/REQ-1-short-slug/`. Состав материалов тот же, что в §2.2; отдельного журнала задачи нет.
- История остаётся в общем журнале со scope `{"type":"request","key":"REQ-1"}`, не global. По этой модели у запроса нет родительского проекта/организации, он не попадает в их выборки; global по-прежнему возвращает только записи с type=global. История доступна через собственный request scope и режим всего журнала.

Для непроектной последовательности принят отдельный уникальный индекс по number WHERE project_id IS NULL (§22): одного UNIQUE(project_id, number) в SQLite для строк с NULL недостаточно.

Правила последующей привязки к проекту не утверждены; разрешение непроектных запросов само по себе не разрешает менять существующие ключи, переносить папки или переписывать историю.

### 2.6. Внутренние ключи

Для id таблиц organizations, projects, requests и request_statuses принят **INTEGER PRIMARY KEY** (§21). Внутренний ключ выдаёт SQLite, он не зависит от переименовываемых полей. Публичные ключи CODE-number/REQ-number и принятые правила requests.number от этого не меняются. Последующим общим пакетом приняты остальные поля, FK и ограничения (M1-START §1; запись §22). Id и number сохраняются оба: внутренний ключ всех запросов не заменяет номер внутри проекта/непроектной последовательности.

## 3. Кто и как меняет статус и прогресс

### 3.1. Явные сценарии вместо наблюдателя за Markdown

Модуль requests предоставляет узкий API: создать, прочитать/список, изменить title/status, зафиксировать progress с путями артефактов. CLI — тонкий вход; filesystem/Git/SQL — адаптеры. Работа с контекстом использует общие механизмы knowledge, а межмодульная координация остаётся в app, без доступа к чужим таблицам и внутренним файлам модулей.

Сейчас API вызывает инженер или ведущий агент по фактическому ходу работы. Позже тот же API сможет вызывать flow. Само создание записи, изменение Markdown или наличие файла report не запускает выполнение и не переводит задачу в done. Смысловой результат оценивает ведущий работу, не SQL-адаптер; будущая автоматическая приёмка определяется юнитом/flow, не глобальным human-only правилом.

| Действие | SQL-карточка | Артефакты задачи и общий журнал |
|---|---|---|
| Зафиксировать запрос | ID, project (или NULL), number, title, status_id по явно переданному code, context_dir, даты; без статуса по умолчанию (§20) | Исходник и первая запись журнала |
| Начать/сменить этап работы | Явно выбрать research/planning/in_progress/review, обновить updated_at | Запись фактической смены статуса с пояснением |
| Остановить работу временно | Явно выбрать blocked или paused, обновить updated_at | Причина блокировки или паузы |
| Зафиксировать исследование/план/изменение | Status не меняется автоматически; updated_at обновляется | Артефакт и запись о результате/изменении со ссылкой |
| Изменить title | Новый title и updated_at | Краткая запись о переименовании; папка прежняя |
| Зафиксировать конечный исход | Явно установить done/failed/cancelled, updated_at | Итог/причина и ссылки на результат |

### 3.2. Содержание журнала

Текст записи формулирует агент/инженер; CLI назначает event_type по выполняемой операции, добавляет время/ссылку на scope, сохраняет запись в текущем файле общего JSONL-журнала и делает локальный commit. Сохранение новых записей и чтение истории скрывают ротацию за одним Node API. Для смены статуса прежнее/новое значения берутся из подтверждённой DB-операции, а не придумываются LLM. При повторе уже установленного статуса сам по себе новый переход не создаётся.

Примеры текста событий, без фиксации окончательной JSON-схемы (ссылки приведены относительно папки соответствующей задачи):

- «new → in_progress. Начат разбор текущей реализации».
- «Сравнены два способа авторизации, выбран второй; исследование: research/auth.md».
- «План уточнён после проверки ограничений API; изменены пункты 2–3: plans/plan-v2.md».
- «Обнаружен тупик: библиотека не поддерживает нужный режим; детали: research/limitations.md».
- «in_progress → done. Изменение проверено; результат и проверки: artifacts/result.md».

Под «все изменения» понимаются значимые изменения карточки, постановки задачи, планов/исследований и фактические исходы работы, которые проводятся через API. Полный побайтовый diff хранит Git. Не логируем каждый tool call, токен, сохранение редактора или внутреннюю SQL-команду.

Ручное редактирование Markdown само не обновляет status/updated_at и не создаёт журнальную запись. Ведущий агент явно фиксирует итог изменения через API; никаких watcher-ов и автоматического толкования текста. Полной истории действий в обход API этот вариант не обещает. updated_at — время учтённой активности, а не filesystem mtime любого вложенного файла.

### 3.3. Статусы и расширение

По запросу инженера принят начальный набор из **10 статусов** (запись §11). Это начальные данные справочника request_statuses, не закрытый перечень в коде (§18):

| Статус | Значение |
|---|---|
| `new` | Запрос зафиксирован, работа ещё не начата |
| `research` | Изучение задачи, ограничений и вариантов решения |
| `planning` | Подготовка или уточнение плана |
| `in_progress` | Выполнение основной работы; также общий рабочий статус без выделения более конкретного этапа |
| `review` | Проверка результата; не обязательно человеком |
| `blocked` | Продолжению мешает конкретное препятствие |
| `paused` | Работа осознанно отложена, без обязательного блокирующего препятствия |
| `done` | Результат запроса получен |
| `failed` | Запрос завершён неудачно, а не просто упала отдельная попытка |
| `cancelled` | Решено не выполнять или прекратить запрос без завершения |

Это доступные состояния запроса, **не обязательная цепочка этапов**. Research/planning/review можно пропускать или возвращаться к нужному незавершённому этапу по ходу работы; отдельный flow engine для этого не нужен. Из new можно перейти прямо к конечному исходу по факту выполненной/отменённой работы. Повтор текущего статуса — no-op, не новый переход. Статус меняется явно, с пояснением в общем журнале; SQL/наличие файла не оценивают смысл результата. Рабочий статус не доказывает наличие запущенного процесса агента.

Blocked и paused — не терминальные: после устранения причины явно выбирается актуальный рабочий статус. Причина ожидания/паузы хранится в журнале, не требует отдельных SQL-полей blocked_reason/previous_status/paused_until. Неудача команды, теста или отдельной попытки сама не переводит запрос в failed. Failed обозначает конечный неуспешный исход запроса; если работу продолжают, фиксируют ошибку в журнале и сохраняют соответствующее рабочее состояние/blocked.

В начальном наборе терминальные состояния — **done, failed, cancelled**; у них is_terminal=true, у остальных семи — false. При работе терминальность читается из справочника, а не определяется отдельным списком имён в коде. Терминальные запросы не reopen-ятся; продолжение — новый связанный запрос. Пока достаточно явной ссылки на прежнюю задачу в контексте, без таблицы графа связей на будущее. Review/done не вводят обязательной глобальной приёмки инженером: будущая приёмка по-прежнему определяется юнитом/flow.

#### 3.3.1. Принятый справочник статусов

Принят request_statuses (§18), принадлежащий модулю requests; его устойчивый ключ и связь с карточкой уточнены в §19:

| Поле | Содержание |
|---|---|
| `id` | Устойчивый внутренний ключ статуса, INTEGER PRIMARY KEY (§21); не меняется при переименовании |
| `code` | Уникальное переименовываемое машинное имя, по которому CLI находит статус |
| `is_terminal` | Завершает ли статус запрос |

- requests.status_id ссылается внешним ключом на request_statuses.id. CLI/API разрешает введённый code через справочник и сохраняет найденный id; допустимые имена для ошибки CLI берутся из той же БД. Неизвестный code отклоняет API, несуществующий status_id — API и FK с включёнными внешними ключами SQLite.
- При создании статус — обязательный явный вход (§20). Ведущий LLM-агент выбирает подходящий code из актуального справочника и передаёт его CLI; инженер также может задать его явно. CLI/core не вызывает LLM и не выводит статус из исходника/артефактов. Отсутствующий или неизвестный code — ошибка, не подстановка new. Сразу сохраняется id выбранного статуса, без обязательного промежуточного new. Ни is_initial, ни настройки/default начального статуса нет; new — обычный переименовываемый статус, не специальная роль.
- Переименование меняет только code одной строки справочника, сохраняя id и is_terminal. Карточки запросов, их status_id и updated_at не меняются; каскадное обновление ссылок и фиктивные переходы состояний не нужны. Уникальность code сохраняется. Это не reopen; старые тексты JSONL остаются как были.
- Фиксированный TypeScript enum/union допустимых имён и CHECK (status IN (...)) не используются как второй перечень. Все входы обращаются к общему API requests; справочник не дублируется в конфиге или Markdown как управляемое состояние.
- Добавление статуса — обычная транзакционная запись в справочник, без изменения кода и миграции схемы. Начальные 10 значений нужны при инициализации новой БД, но не должны перезаписывать изменённый справочник при каждом запуске. Миграции по-прежнему нужны при изменении структуры БД, не для каждого нового значения статуса.
- Удаление используемого статуса запрещено внешним ключом. Замена требует явного решения о соответствующих запросах; каскадного удаления задач нет. Изменение is_terminal используемого статуса запрещено (§22); для другого поведения создаётся другой статус. Это не допускает массового закрытия или переоткрытия запросов изменением справочника.
- Добавить допустимый код не значит добавить специальное поведение агента: такая логика может потребовать изменения кода. Явный выбор при создании заменяет механизм общего начального статуса (§20). Предложения is_initial и запрета переименования new ради поиска по строке отклонены; универсальное управление workflow этим решением не вводится. Прежние записи JSONL не переписываются.

Расширяемость обеспечивают ID, один адрес контекста, узкий API и миграции структуры при необходимости. Когда появятся требования исполнения, добавим необходимые поля/отношения. Сейчас нет flow_id/run_id/step/attempt, leases, workflow DSL, универсального event bus или таблиц technical operations.

### 3.4. Честная граница сохранения

Принятая граница затрагивает DB + файлы + Git. Они **не становятся одной атомарной транзакцией**. Не переносим автоматически отозванный recovery engine обратно в проект. Принят контракт partial и продолжения после явной сверки (M1-START §3; запись §22). Последовательности эффектов сценариев:

- Создание: выделить номер и определить один context_dir, сохранить исходник без overwrite, зарегистрировать карточку с выдаваемым SQLite id, добавить запись о регистрации и локальный git commit. Если SQL-регистрация не удалась, сохранённый исходник не удаляется; частичный результат и путь сообщаются явно.
- Смена status/title: SQL-транзакция подтверждает изменение, затем фиксируются соответствующая запись журнала и локальный commit. Не пишем «done» в журнал до успешного изменения БД.
- Progress с артефактами: сохраняются явно перечисленные материалы и запись журнала, делается локальный commit, затем обновляется время учтённой активности в БД. Status при этом не угадывается из текста.
- Полный успех возвращается только после завершения всех частей выбранного сценария. При частичном успехе CLI возвращает ненулевой exit code и результат partial: ID, если карточка существует, путь контекста, подтверждённо сохранённые и оставшиеся части. Не маскирует SQL-успех под rollback и не стирает чужие изменения; в commit идут только изменения операции.
- При частичном результате агент сверяет БД, файлы, журнал и Git и через общий API завершает только недостающее. Не повторяет создание существующей карточки, overwrite исходника или append вслепую. Если точную историю потерянного перехода восстановить нельзя, фиксирует note о проверенном текущем состоянии, не выдумывает переход. Повреждённые или неоднозначные данные — остановка с диагностикой. Автоматический retry/resume не обещается.

Принятая простая основа не гарантирует атомарный, exactly-once audit-log каждого перехода при любом обрыве процесса. Потерянный ответ/оборванный append могут потребовать явной сверки, а отсутствие записи в журнале не отменяет DB-статус. Если нужен именно безусловно полный аварийно-устойчивый audit, это отдельное требование и цена дополнительного механизма; сейчас оно не принимается за инженера. Для M1 выбран человеческий журнал с явными частичными ошибками, не такой audit engine.

Git commit контекста не означает remote sync или backup БД. БД по-прежнему требует отдельного backup; папка задачи не восстанавливает весь реестр, текущие состояния или общий журнал автоматически.

### 3.5. Общий журнал, ротация и выборки

Один логический журнал состоит из помесячных JSONL-файлов в git контекста: **`home/journal/YYYY-MM.jsonl`**, например `home/journal/2026-10.jsonl`. Принято в §12. Месяц определяется временем самой записи в UTC, назначенным CLI/core, а не локальным часовым поясом или датой создания задачи. Каждая физическая строка — отдельная JSON-запись; многострочный текст остаётся значением строки с JSON-экранированием.

Файл создаётся при первой записи соответствующего месяца; пустые файлы заранее не создаются. Записи дописываются в конец, прежние записи не переписываются, старые файлы не переименовываются. Отдельный процесс ротации, сжатие и настройки размера файла не вводятся.

- БД выбирает запросы/проекты и разрешает связи scope. Записи истории читаются из JSONL файловым адаптером; SQL-запрос сам по себе не ищет в этих файлах. Нет таблицы-копии журнала, каталога offsets, FTS или постоянного поискового индекса.
- CLI/API поддерживает чтение истории запроса, проекта и организации. Для события проектной задачи связь с родителями можно разрешить по request ID через БД, у REQ-number таких родителей нет; не надо заранее дублировать все названия в каждой строке. Формат scope для записей задачи и вне задач принят в §3.7, обязательный event_type — в §3.6/§13; вся JSONL-оболочка принята в §3.6/§14. Фильтр event_type позволяет выбрать, например, только смены статусов без разбора свободного текста; применяется вместе с фильтрами scope/дат до общего порядка и limit.
- Reader учитывает все файлы нужной ротации, не только текущий. Без ограничения периода просматриваются все месячные файлы; при заданном диапазоне дат — файлы соответствующих месяцев UTC, с проверкой точного диапазона по времени самих записей. История одной задачи может пересекать сколько угодно месяцев. Чтение потоковое, фильтрация по scope/датам до выдачи результата агенту; порядок и limit относятся к общей выборке, не к каждому файлу отдельно.
- Ссылки на артефакты выдаются с контекстом соответствующей задачи/однозначным путём, а не трактуются как относительные к общей папке журнала.
- Scoped warmup и scoped-поиск не получают чужие записи только потому, что физический журнал общий. Один читатель/писатель используется всеми входами; ротация не создаёт отдельную бизнес-логику в scripts/ или отдельный runner.
- Ротация означает разбиение файлов, **не автоматическое удаление истории**. Нельзя молча исключать старые файлы из результата. Политика retention сейчас не добавляется.
- Без индекса стоимость выборки зависит от объёма прочитанных файлов. Для M1 принимается простое сканирование; не создаём индексирование или поисковый сервис ради предполагаемого роста.

JSONL не меняет границу §3.4: не обеспечивает общей транзакции с SQLite/Git и не превращает историю в event sourcing. Независимой редактируемой Markdown-копии журнала нет; при необходимости CLI форматирует выбранные записи для чтения.

### 3.6. Принятая минимальная JSONL-запись

JSONL-оболочка принята полностью (§14); scope ранее принят в §3.7/§10, обязательный event_type — в §13. Четыре обязательных поля — at, scope, event_type, text; одно необязательное — artifacts:

| Поле | Содержание |
|---|---|
| `at` | Время записи в UTC, ISO 8601; назначает CLI/core |
| `scope` | Один адресат записи: type и, кроме global, key; полный контракт принят в §3.7 |
| `event_type` | Обязательный тип события: note/request_created/status_changed; назначает CLI/core по операции |
| `text` | Непустой текст исхода/прогресса, сформулированный агентом или инженером |
| `artifacts` | Необязательный массив путей к материалам, относительно home |

Принятый начальный набор event_type:

| Значение | Что произошло |
|---|---|
| `note` | Зафиксированы прогресс, решение, результат или тупик; любой допустимый scope |
| `request_created` | Зарегистрирован запрос; scope=request |
| `status_changed` | Явно изменён статус запроса; scope=request |

Scope отвечает «к чему относится запись», event_type — «что произошло», text поясняет детали. Тип назначается выполняемым сценарием CLI/core, не угадывается по тексту LLM. Повтор уже установленного статуса не создаёт status_changed. Новые типы добавляются по реальной необходимости; поле не запускает обработчики/flow и не превращает журнал в источник состояния вместо БД.

Один JSON-объект на физическую строку. Многострочный text сохраняется значением строки с экранированием, не разрывает запись на несколько строк файла. Пути artifacts имеют единую базу home для любого scope, не зависят от расположения/имени файла ротации. CLI может принимать путь относительно задачи, но перед сохранением разрешает его через context_dir и приводит к home-relative. Абсолютные пути и выход за контекстный root не принимаются.

```jsonl
{"at":"2026-10-02T12:00:00Z","scope":{"type":"request","key":"MP-23"},"event_type":"request_created","text":"Запрос зарегистрирован."}
{"at":"2026-10-02T12:10:00Z","scope":{"type":"request","key":"MP-23"},"event_type":"status_changed","text":"new → research. Начато исследование вариантов ротации."}
{"at":"2026-10-02T12:30:00Z","scope":{"type":"request","key":"MP-23"},"event_type":"note","text":"Сравнены варианты ротации журнала.","artifacts":["projects/prineycom/mypi/requests/MP-23-add-jsonl-journal/research/rotation.md"]}
{"at":"2026-10-02T13:00:00Z","scope":{"type":"project","key":"MP"},"event_type":"note","text":"Обновлён глоссарий проекта."}
{"at":"2026-10-02T13:30:00Z","scope":{"type":"request","key":"REQ-1"},"event_type":"note","text":"Сохранены материалы запроса без проекта.","artifacts":["requests/REQ-1-short-slug/research/result.md"]}
```

Это иллюстративные события, не реальные исходы этой сессии. Для организации принят scope `{"type":"org","key":"prineycom"}`, для общей записи — `{"type":"global"}` без выдуманного global ID. Scope request использует короткий ключ `MP-23` или `REQ-1`, не basename папки, title или внутренний SQL id. Неизвестный/неоднозначный scope — ошибка, не молчаливое переназначение на global.

Запись задачи не повторяет project/org: CLI разрешает существующих родителей по БД. У REQ-number нет родительского проекта/организации, его записи не включаются в их выборки и не становятся global. Выборка проекта включает его собственные события и события его задач; выборка организации — её события и события дочерних проектов/задач. Это требует только связей реестра и потокового фильтра файлов ротации, не индекса журнала. Пример события задачи хранит один канонический record, не отдельную копию для каждого уровня.

Переход статуса пока можно записывать text-строкой вида «new → in_progress. Начат разбор»; текущий статус и фильтрация задач по статусу — через БД, не парсинг этой фразы. Event_type=status_changed позволяет отбирать переходы, но прежнее/новое значения пока остаются в text. Не добавляются event ID, actor/session/run или произвольный metadata-объект без текущего сценария их использования. Если артефактов нет, поле artifacts опускается, а не заполняется пустым массивом или null. Пустые поля/null-плейсхолдеры не нужны. JSONL-схема не обещает дедупликацию повторов или audit-гарантии сверх §3.4.

### 3.7. Принятый scope-контракт M1

Scope отвечает только на вопрос «к чему относится запись», не «кто её создал» или «какой это этап работы». Для M1 приняты ровно четыре варианта; это закрытый текущий набор, не перечень всех возможных будущих сущностей.

| type | Все допустимые поля scope | Значение key | Пример |
|---|---|---|---|
| `global` | `type: "global"` | Поля key нет | `{"type":"global"}` |
| `org` | `type: "org"`, `key: string` | Канонический slug организации из БД | `{"type":"org","key":"prineycom"}` |
| `project` | `type: "project"`, `key: string` | Уникальный буквенный код проекта | `{"type":"project","key":"MP"}` |
| `request` | `type: "request"`, `key: string` | Короткий ключ задачи CODE-number или REQ-number без проекта | `{"type":"request","key":"MP-23"}` или `{"type":"request","key":"REQ-1"}` |

Принятые правила записи:

- type обязателен и совпадает с одним из четырёх значений. У org/project/request key обязателен, непустой и разрешается через реестр БД; у global он отсутствует, не null/пустая строка/фиктивный ID.

Request key — `[A-Z]+-[1-9][0-9]*`; для REQ-number ищется непроектный запрос, а не проект REQ. Сам regex не заменяет проверку существования в БД. Значение `MP-23-add-jsonl-journal`, путь или title не являются key.
- У записи ровно один наиболее конкретный scope. Событие задачи получает request scope; проект и org разрешаются через связи БД, если они есть. Отсутствие проекта у REQ-number не меняет тип scope на global. Событие проекта без конкретной задачи получает project scope. global предназначен для действительно общих исходов, а не для неизвестного адресата.
- В scope не дублируются project_id/org_id/request_id, пути или имена. Дополнительные поля, массив scope, неизвестный type, отсутствующий/неизвестный key — ошибка записи, не автоматическое расширение формата или fallback в global. При чтении неподдерживаемая/повреждённая запись не маскируется как корректная global-запись.
- Не добавляем отдельные scope `task` (здесь это request), `flow`, `agent`, `session`, `system`, `artifact` или `all`. Flow/сабагенты пока отсутствуют; артефакт — ссылка в artifacts, а не новый адресат журнала. Расширение набора возможно с реальной функцией, не заранее.
