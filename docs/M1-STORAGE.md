# M1 — хранение, capture и восстановление операций

Статус: **предложение отозвано как преждевременное усложнение; не основание для реализации**.
Актуальная граница M1 — [M1-REQUESTS.md](M1-REQUESTS.md): организации, проекты, запросы инженера и их статусы/прогресс. DB-capture, универсальные `operations`/`operation_files` и recovery engine не приняты. Конкретный XDG-путь, DB-only project add без скелета и прочие детали этого предложения также не утверждены.

Ниже сохранено прежнее предложение и запись его подготовки; это история обсуждения, не действующие требования. Принятые независимо стек и модульные границы — [M1-DESIGN.md](M1-DESIGN.md), граница DB/git — [M0-CONTRACT.md](M0-CONTRACT.md).

## 1. Рекомендуемая граница данных

| Данные | Каноническое хранение | Как сохраняются |
|---|---|---|
| Реестр организаций/проектов, локальная привязка checkout | SQLite | Одна SQL-транзакция |
| Capture: идентичность, исходный текст, время получения | SQLite | Одна SQL-транзакция; без файлового append и git commit |
| MEMORY, glossary, journal/errors, notes, ADR и артефакты | Markdown/файлы в отдельном git `home/` | Файловая операция + локальный commit; receipt/recovery в SQLite |
| Незавершённая запись контекста | Служебный план операции в SQLite | Устойчивое намерение до файлового эффекта |
| История закоммиченного контекста | Git `home/` | Не заменяет DB backup |

**Capture предлагается хранить целиком в БД**, а не разносить identity в SQLite и source в отдельный файл. Это убирает двухфазное сохранение из самого частого простого ввода. Текст всё равно доступен агенту через чтение по ID; Markdown-представление не становится вторым редактируемым оригиналом.

Контекст не переносится целиком в SQL: MEMORY и заметки остаются файлами, не проекциями таблиц. Временный recovery payload — замороженный план записи, не альтернативное редактируемое хранилище знаний.

`project add` предлагается сделать DB-only: зарегистрировать org/project и существующий checkout одной транзакцией, **без пустого файлового скелета**. Каталоги контекста создаются первой необходимой записью; отсутствие MEMORY/glossary при чтении нормально. Это явное отличие от legacy. Уже существующий контекст сохраняется. Повтор той же привязки — no-op; другая привязка под тем же ID не перезаписывает старую молча.

## 2. Физическое размещение

Предлагаемый Linux default:

```text
home/                                      # отдельный git контекста
  MEMORY.md, notes/, <org>/<project>/...

${XDG_STATE_HOME:-~/.local/state}/mypi/
  stores/<key>/
    state.sqlite                           # авторитетная БД
    writer.lock                            # штатная OS-блокировка
```

`key` автоматически вычисляется как SHA-256 канонического абсолютного пути `home/` после `realpath`. Это локальный ключ размещения, не переносимая identity проекта. Он не требует пользовательского config-поля и не смешивает БД разных контекстных roots. Фактический путь выводится в диагностике.

- DB и её служебные файлы должны физически находиться вне git движка, контекста и рабочих проектов. Нестандартный XDG-путь внутри такого репозитория — ошибка, а не причина полагаться на `.gitignore`.
- Root и state инициализируются явно, не из `warmup`, `show`, `list` или при неожиданной потере БД. Отсутствие ожидаемой БД — диагностируемая ошибка, не «пустое новое хранилище».
- Переименование/перенос `home/` меняет вычисляемый путь. Нужна явная привязка перенесённого состояния при переносе/restore; автоматического поиска и выбора похожей БД нет. Полный протокол переноса сюда не входит.
- `checkout_path` проекта — необходимая локальная привязка, а не identity; существование и разрешение symlink проверяются при действии.
- Права каталогов/БД ограничиваются текущим пользователем. Это не шифрование и не sandbox от других процессов того же пользователя.

Для начального SQLite-адаптера предлагаются `foreign_keys=ON`, rollback journal (`DELETE`) и `synchronous=FULL`: короткие транзакции, один локальный writer, без преждевременного WAL-тюнинга. Выбор WAL позже должен опираться на измеренную потребность; ни один режим не делает SQLite и Git общей транзакцией.

## 3. Минимальная логическая схема

Это состав данных и constraints, **не готовая SQL-миграция**. Физические типы/индексы уточняются при разрешённой реализации.

| Таблица | Минимальные данные | Владелец и назначение |
|---|---|---|
| `organizations` | `slug` — PK | projects; зарегистрированный org scope |
| `projects` | `org_slug` — FK, `slug`, `checkout_path`, `created_at`; PK `(org_slug, slug)` | projects; identity и локальная привязка |
| `captures` | `id` — PK, `source_text`, `created_at` | inbox; неизменяемый исходник явного capture |
| `operations` | `id` — PK, `kind`, `input_hash`, `created_at`, `state`, receipt; для контекстной записи — ожидаемый Git ref/base commit и итоговый commit | app/recovery; повтор операции и незавершённое сохранение |
| `operation_files` | FK на operation, относительный путь; ожидаемые before/after состояния и целевые байты | app/recovery; точный write set незавершённой операции |
| `schema_migrations` | `version` — PK, checksum, время применения | infrastructure/database; порядок и идентичность SQL-миграций |

Constraints и правила:

- `org/project` — ровно два безопасных сегмента; scope/пути проверяются на всех входах, включая импорт и чтение реестра. FK/unique/check constraints дополняют доменную валидацию, а не заменяют её.
- Глобальный scope — отсутствие org/project, не фиктивная строка `global` в таблицах. Первый `project add` создаёт org и project атомарно.
- Capture ID можно использовать равным ID операции capture: одна команда создаёт один исходник. Время фиксируется один раз, не меняется при восстановлении.
- В `operations` только технические состояния `pending` и `completed`, не lifecycle задачи. Ошибка валидации до эффектов не создаёт pending-запись. Ошибка сохранения после prepare оставляет pending с диагностикой; конфликт не маскируется терминальным «успехом».
- Receipt — небольшой устойчивый результат команды, например ID записи или путь/commit. Это не дубликат всего контекста и не общий event store. Payload формата операции валидируется по её конкретному kind, без универсального workflow DSL.
- `operation_files` хранит относительные пути внутри данного context root. Before-состояние включает отсутствие файла либо ожидаемые bytes/hash и существенные атрибуты; after — точное ожидаемое состояние. Для существующего чистого файла preimage уже адресуется исходным Git commit. Целевые байты нужны для продолжения без повторного вычисления append.
- После завершения тяжёлый recovery payload очищается транзакционно; ID/input hash, receipt и метаданные подтверждения остаются для retry. Незавершённый payload автоматически не удаляется. Политику удаления receipts нельзя вводить без явной границы гарантии повторов.
- Сейчас **нет** таблиц memory facts, notes, requests, runs, steps, leases, acceptance или поискового индекса на будущее. Схема импорта добавляется при проектировании самой миграции, не предположительно.

Доменные таблицы принадлежат своим модулям из M1-DESIGN. App координирует транзакцию/receipt через узкие порты, но не становится универсальным repository для предметных данных.

## 4. Capture: исходник и повтор команды

### Исходник

`source_text` содержит полученный валидный Unicode-текст без trim, нормализации Unicode, исправления орфографии, перевода строк или добавленного заголовка. Сохраняются пробелы, пустые строки и завершающий newline. Для UTF-8 файлового/stdin-ввода повреждённая кодировка должна отвергаться, а не заменяться символами-заглушками. Для argv граница сохранности начинается после разбора оболочкой: CLI не может восстановить кавычки исходной shell-команды.

ID/время/оформление — отдельные метаданные или представление. Оригинал не редактируется командой «оформить». M1 не придумывает для capture статусы задач, project field, связи с flow или автоматический запуск.

Общий warmup выдаёт ограниченный индекс с ID и кратким представлением; полное чтение по ID возвращает весь source, а не первую строку. Scoped warmup не читает общий inbox. Raw-чтение должно отделять source от служебного вывода, чтобы не добавлять к нему оформление.

### Идемпотентность

**Одинаковый текст не означает одну операцию.** Два намеренных capture с одним текстом допустимы.

Для каждой изменяющей команды есть operation ID. CLI генерирует его до эффектов и показывает; вызывающий API может передать устойчивый ID заранее. При явном повторе используется **тот же ID**; конкретное написание retry-опции CLI ещё не фиксируется.

- Новый ID + валидный capture: source и completed receipt записываются одной SQL-транзакцией.
- Тот же ID + тот же kind/input hash: возвращается прежний результат; второй capture не создаётся.
- Тот же ID + другой ввод: ошибка конфликта, не замена текста.
- Тот же ID для pending-контекстной операции: продолжение её сохранённого плана после проверки условий.
- Новая команда без прежнего ID считается новым намерением. Потерянный ответ не позволяет надёжно отличить retry от второго одинакового capture по тексту/времени. Если ID утрачен, сначала читаются receipts; повтор «вслепую» не обещает exactly-once.

Input hash считается по однозначному представлению входа, включая kind/scope/source, но без вновь сгенерированного времени и других случайных значений. Формат этого представления версионируется с протоколом. Completed-операция не reopen-ится; новое намерение получает новый ID.

### Граница с legacy

После разрешённой миграции `home/inbox.md` больше не является активным inbox новой системы. Исходный legacy-файл сохраняется как свидетельство миграции, а не удаляется/переписывается ради чистоты схемы. Старый CLI пока не меняется.

Multiline legacy-текст может содержать строки, неотличимые от начала следующей записи. Без надёжной границы нельзя обещать автоматическое восстановление исходных capture: неоднозначный фрагмент сохраняется целиком и требует явного разбора. Повторяемость импорта и mapping старых записей проектируются отдельно; дедупликация только по source hash недопустима.

## 5. Один writer, без нового supervisor

Нужна одна стандартная локальная advisory-блокировка на context store для всех изменяющих входов: CLI и будущих Node API-адаптеров. Блокировка удерживается на всём протяжении файлов/Git/DB-протокола. Конкретная готовая OS/Node-интеграция ещё не выбрана; свой lock scheduler, TTL lease и определение владельца только по PID не предлагаются.

Важное требование к реализации: авария родительского Node не должна позволить второму writer продолжить, пока старый Git-потомок ещё способен менять хранилище. Нужен kernel-owned lock с корректным удержанием дескриптора участниками записи либо другой доказанный штатный механизм. Один lock только в памяти Node этого не обеспечивает. Эта граница проверяется реальным restart-тестом до приёмки адаптера.

После получения блокировки наличие чужой pending-операции запрещает новую запись до её явного recovery. Захват блокировки имеет конечное ожидание/ошибку busy, не вечный retry.

Составные read-only команды получают согласованный доступ к context store и проверяют pending-состояние. Они не завершают чужую запись автоматически: при незавершённой контекстной операции сообщают `recovery required`, а не выдают смесь файлов за целый снимок. Открытие отсутствующего хранилища не запускает bootstrap. Read path не создаёт MEMORY, schema или пользовательские файлы.

Блокировка координирует mypi, не обычный редактор или произвольный `git` в другом терминале. Для внешних изменений действуют preconditions и отказ при конфликте; строгой атомарности с неконтролируемым параллельным редактором не обещается. Все проверки пути повторяются перед записью; symlink/выход за root не допускаются. Это не защита от враждебного процесса с теми же правами ОС.

## 6. Протокол контекстной записи

Пример: journal, note, memory add/remove. Вместо «append ещё раз» сохраняется заранее вычисленный конечный результат.

Для позиционного удаления MEMORY номер из предыдущего чтения должен сопровождаться ревизией файла: устаревший номер не должен удалить уже другой факт. Ревизия вычисляется при чтении, не задаётся в конфиге; конкретный CLI-синтаксис ещё не выбран. Новая операция проверяет её до prepare, а recovery использует уже сохранённый write set.

1. **Проверить условия под writer lock.** Home — нужный отдельный Git, нет merge/rebase и незавершённой операции. Участвующие пути чисты относительно HEAD и индекса; новый путь отсутствует. Посторонний dirty/staged diff допустим, но не включается в commit. На целевом пути чужие незакоммиченные изменения — безопасный отказ до prepare, без stash/reset и автоматического commit чужого текста.
2. **Подготовить план.** Один ID, timestamp, пути, before/after состояния, точные after-байты, ожидаемые Git ref/HEAD. Отсутствие HEAD допускается как явно записанная исходная граница первого commit; recovery не путает её с потерей существующей истории. Для note путь содержит уникальный ID, не только дату/slug. Проверить отсутствие выхода за root и возможность операции. Сохранить pending operation + write set одной DB-транзакцией **до изменения контекста**.
3. **Записать файлы.** Для каждого пути: before → установить after; уже after → ничего не дописывать; иной результат → конфликт. Используется безопасная атомарная замена отдельного файла через временный файл на той же FS; создание нового файла — без overwrite. Буферы записи не становятся частью git commit и не заменяют устойчивый план в DB. Между несколькими файлами атомарности нет — её заменяет проверяемое продолжение.
4. **Сделать локальный commit только write set.** Проверить ожидаемые ref/HEAD и сохранность постороннего индекса; commit содержит operation ID в trailer. Результат проверяется по parent, путям, blob-содержимому и ID, не только exit code. Git adapter не должен незаметно запускать сеть через hooks/filters/подпись; неподдерживаемая конфигурация требует отказа до эффектов, а не изменения глобального Git config. Конкретная реализация selective commit проверяется отдельно на staged/unstaged чужих изменениях.
5. **Закрыть receipt.** Когда нужный commit подтверждён, одной SQL-транзакцией записать его OID, completed receipt и убрать тяжёлые временные payload. Только затем сообщать полный успех. Успех DB-only означает DB commit; успех контекстной команды — также подтверждённый локальный Git commit, не sync/backup.

При отказе после prepare команда возвращает ненулевой результат, operation ID, фактически достигнутую границу и способ явного продолжения. Она не удаляет intent, не повторяет append и не откатывает чужую работу. Если безопасный rollback не доказан, используется forward recovery либо остановка для разбора, не «компенсация любой ценой».

Операция, не меняющая данные, не порождает пустой git commit; её no-op receipt сохраняется отдельно. Запись и cleanup одного файла не превращаются в shell-скрипт с собственной бизнес-логикой: протокол находится в app, эффекты — в адаптерах.

## 7. Что делает recovery после сбоя

Recovery запускается явно для существующего ID и сначала получает ту же блокировку. Фазы определяются по сохранённому плану и фактическим файлам/Git, а не по оптимистичному флагу «мы уже вызвали commit».

| Устойчивая граница сбоя | Наблюдаемое состояние | Действие |
|---|---|---|
| До DB prepare | Нет операции, нет её эффектов | Новая попытка может начать запись |
| После prepare, до файлов | Pending, все файлы before | Установить сохранённый after, затем commit |
| После части/всех файлов, до commit | Pending, допустимая смесь before/after | Довести только before; не append повторно |
| Git отказал или не успел commit | Pending, файлы after; возможны промежуточные изменения индекса | Продолжить только после проверки, что промежуточное состояние принадлежит этому write set; чужое/неясное — конфликт |
| Git commit есть, финальная DB-транзакция не завершилась | Pending; в текущей истории есть подтверждённый commit этой операции | Зафиксировать его OID/receipt, без повторной записи и второго commit |
| DB завершила операцию, ответ потерян | Completed receipt | Вернуть сохранённый результат по тому же ID |
| Файлы, HEAD/ref или index расходятся с допустимыми состояниями | Необъяснимое внешнее изменение | Остановиться с конфликтом; сохранить intent/данные для разбора |

Для поиска потерянного commit недостаточно совпадения текста сообщения: нужны ожидаемый parent, точный write set и blob-содержимое. Если после него появились новые commits, подтверждение допустимо только при проверенной достижимости и отсутствии противоречия результату операции; иначе явный конфликт. Сброшенная/переписанная история не «исправляется» автоматическим reset.

Индекс Git тоже входит в протокол: нормальный путь не коммитит и не стирает чужие staged changes; recovery распознаёт только разрешённые промежуточные изменения своих путей. Неизвестный `.lock` Git нельзя удалять по таймеру или только потому, что родительский PID исчез. При недоказанной безопасности требуется диагностика, не захват чужого lock.

Целевой сценарий этого предложения — аварийное завершение процесса и потеря ответа. Гарантии при отключении питания требуют отдельно проверить fsync файлов/каталогов, durability Git objects/refs и порядок с DB commit; одна `synchronous=FULL` их не доказывает. До таких проверок power-loss safety не заявляется.

**Crash recovery не равно backup/restore.** Если потеряна сама БД вместе с pending-планом, нельзя восстановить всё по Git и выдать новую БД за прежнее состояние. Нужен отдельный consistent DB backup и согласованный контекст; расписание/retention и полный restore-протокол сюда не добавляются.

По [TESTING.md](TESTING.md), без новой платформы тестов и без численных обещаний до замеров:

- Boundary: reopen после DB commit, реальный selective Git commit с посторонним staged/unstaged diff, отказ на dirty target, abrupt termination/restart на устойчивых границах §7 и удержание writer lock живым потомком.
- Проверять наблюдаемый результат: один capture/исход, сохранный source, правильный commit, сохранность чужих данных, отсутствие молчаливого overwrite и записи при чтении. Исключение в mock не доказывает поведение после SIGKILL.
- Большая матрица повторов не размножается через CLI. Независимый review и фактические границы стоимости остаются обязательными по принятой политике.

До реализации предстоит проверить осуществимость стандартной lock-интеграции и selective Git adapter. Это не разрешение сейчас устанавливать зависимости, делать пробные записи в личное хранилище или создавать свой supervisor.
