Архитектура решения

Один pnpm-пакет, модульный монолит. Предметные модули задают сценарии и порты; адаптеры реализуют хранение. Слой приложения связывает модули, не создавая универсальную систему операций или восстановления.

App — составные операции

БД, файлы и Git не образуют общую транзакцию. Порядок действий и частичный результат определены явно.

Почему здесь нет дополнительных подсистем
  • Нет microservices, ORM, DI container, event bus и CQRS.
  • Нет flow, исполнителя агентов, табов, сетевой синхронизации и многомашинной работы.
  • Нет captures/operations-таблиц, универсального recovery engine и SQL-индекса истории.
  • Запрос необязателен для обычной работы; capture и регистрация задачи не запускают её исполнение.
  • Core не вызывает LLM. Отдельный ревьюер использовался при разработке, не добавлен в продукт.

Checkout — исходный проект

Необязательный существующий путь хранится в карточке проекта.

Это не его identity и не папка контекста.

Ветки рабочих клонов не переключались; код проектов не коммитился.

id — внутренняя глобальная идентичность. number — номер внутри проекта или общей последовательности REQ. Ключ MP-7 вычисляется из кода проекта и номера; изменение title не меняет ключ и папку.

У задачи нет отдельного журнала. В SQL нет копии source_text или progress. Исходная формулировка сохраняется без trim, заголовков и потерь BOM/CRLF. Опубликованная ссылка указывает на неизменяемую версию артефакта; новая версия получает новый путь.

Статусы и ограничения

Статусы — строки БД, не TypeScript enum и не обязательный pipeline. Начальный код всегда указывается явно, в том числе при создании сразу terminal.

new · research · planning · in_progress · review · blocked · paused · done · failed · cancelled

Последние три — terminal в начальном справочнике. Используемому статусу нельзя изменить terminality или удалить его. Переименование кода сохраняет status_id, не создаёт переход и не меняет updated_at задач. Продолжение закрытого запроса — новая связанная запись, не reopen.

Фактическая SQL-миграция 001
CREATE TABLE organizations (
  id INTEGER PRIMARY KEY,
  slug TEXT NOT NULL UNIQUE CHECK (length(trim(slug)) > 0)
) STRICT;

CREATE TABLE projects (
  id INTEGER PRIMARY KEY,
  org_id INTEGER NOT NULL REFERENCES organizations(id) ON DELETE RESTRICT,
  slug TEXT NOT NULL CHECK (length(trim(slug)) > 0),
  code TEXT NOT NULL UNIQUE CHECK (code <> '' AND code NOT GLOB '*[^A-Z]*' AND code <> 'REQ'),
  checkout_path TEXT,
  UNIQUE (org_id, slug)
) STRICT;

CREATE TABLE request_statuses (
  id INTEGER PRIMARY KEY,
  code TEXT NOT NULL UNIQUE CHECK (length(trim(code)) > 0),
  is_terminal INTEGER NOT NULL CHECK (is_terminal IN (0, 1))
) STRICT;

CREATE TABLE requests (
  id INTEGER PRIMARY KEY,
  project_id INTEGER REFERENCES projects(id) ON DELETE RESTRICT,
  number INTEGER NOT NULL CHECK (number > 0),
  title TEXT NOT NULL CHECK (length(trim(title)) > 0),
  status_id INTEGER NOT NULL REFERENCES request_statuses(id) ON DELETE RESTRICT,
  context_dir TEXT NOT NULL UNIQUE CHECK (length(context_dir) > 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (project_id, number)
) STRICT;

CREATE UNIQUE INDEX requests_unassigned_number ON requests(number) WHERE project_id IS NULL;

CREATE TRIGGER used_status_terminality BEFORE UPDATE OF is_terminal ON request_statuses
WHEN OLD.is_terminal <> NEW.is_terminal AND EXISTS (SELECT 1 FROM requests WHERE status_id = OLD.id)
BEGIN
  SELECT RAISE(ABORT, 'Cannot change terminality of a used status');
END;

CREATE TRIGGER used_project_code BEFORE UPDATE OF code ON projects
WHEN OLD.code <> NEW.code AND EXISTS (SELECT 1 FROM requests WHERE project_id = OLD.id)
BEGIN
  SELECT RAISE(ABORT, 'Cannot rename a project code with requests');
END;

CREATE TRIGGER preserve_request_numbers BEFORE DELETE ON requests
BEGIN
  SELECT RAISE(ABORT, 'Saved requests cannot be deleted');
END;

INSERT INTO request_statuses(code, is_terminal) VALUES
  ('new', 0), ('research', 0), ('planning', 0), ('in_progress', 0), ('review', 0),
  ('blocked', 0), ('paused', 0), ('done', 1), ('failed', 1), ('cancelled', 1);
Формат записи журнала — пример
{
  "at": "2026-10-03T08:00:00Z",
  "scope": { "type": "request", "key": "MP-7" },
  "event_type": "note",
  "text": "Проверка завершена; результат сохранён",
  "artifacts": [
    "projects/org/project/requests/MP-7-slug/research/result-v1.md"
  ]
}

На диске это одна физическая JSONL-строка. Нет event ID, actor/session/run или SQL-копии. Многострочный текст экранируется JSON. Повреждённая/оборванная строка вызывает ошибку, а не исчезает из истории.

Если операция сохранилась частично

Создание запроса идёт в порядке source → DB → journal → Git. Номер выбирается под SQLite write reservation; сохранение source выполняется до фиксации карточки. Git не заменяет транзакцию БД.

Это интерактивная схема контрольных точек, не исполнение команды и не модель всех возможных сбоев. Фактический PartialError содержит saved, missing, paths и при наличии requestId; после любой ошибки нужно сверить реальные данные.

  • Сохранённая DB не откатывается ради видимости общего rollback.
  • Осиротевший source не удаляется; --adopt-source разрешён только при точных байтах и ожидаемом пути/номере.
  • Недостающий Git commit завершается явно, без повторного append в журнал.
  • Потерянный переход не выдумывается. В журнал добавляется фактическая заметка о проверенном состоянии.
  • Для недостающего времени активности есть request touch.

Никаких обещаний exactly-once audit, автоматического retry или универсального восстановления.

Области журнала и наследование памяти

Сначала CLI разрешает scope через БД, затем читает нужные месяцы и применяет scope/date/type; только после этого общий порядок и limit. Scope не даёт права вернуть соседние данные.

    Синтетические записи для объяснения правила, не личная память. MP и YM в примере принадлежат одной организации; REQ-1 не относится к проекту.

    Важно: журнал global содержит только global-события, а не всё дерево. Наследование MEMORY — отдельное правило: global → организация → проект. Scoped warmup не включает общий inbox и не пересказывает исходники чужих задач.

    Независимое ревью и исправления

    Ревьюер — отдельный процесс Pi, модель openai-codex/gpt-6-astra, без инструментов, расширений, исходного диалога и контекстных файлов. Ему передавались исходники и принятый контракт. Это независимый контекст, не независимый поставщик модели и не человеческая приёмка.

    Перед первым запуском: четыре фиксированные ситуации о parser/oracle/бюджете/дублирующем тесте — 4/4 правильных решения, без повторных попыток. Это узкая проверка поведения, не универсальная оценка ревьюера. Сам ревьюер код не исполнял; ниже отдельно приведены фактические тестовые запуски.

    Последний ответ ревьюера целиком
    **Продуктовое исправление одобряю в рамках уточнённого контракта.** В представленном коде не вижу обычного прикладного входа, который способен закоммитить изменение опубликованного артефакта в обход проверки префикса журнала.

Проверенные по коду маршруты:
- `complete` и `restoreContext` проходят через `core.serialize`: сначала `git.validateJournal()`, затем получение `journal.published()`, затем операция.
- Изменения через memory/inbox/notes используют `texts.create/edit` с тем же барьером.
- `journal`, `requests.progress`, публикация `requests.create` и журналирование `requests.change` также выполняют файлово-коммитную фазу внутри `core.serialize`.
- `importLegacy` явно вызывает `git.validateJournal()` до импорта; при коммите защита артефактов использует `publishedArtifactPaths(root)`.
- `initializeWorkspace` не коммитит артефакты. `cloneContextBundle` разворачивает существующую историю, а не создаёт коммит изменения опубликованного артефакта.

Для исходного сценария обхода — переписать уже закоммиченный журнал, убрав сведения о публикации, затем изменить артефакт — проверка обнаруживает несовпадение с префиксом из `HEAD`. В workspace она выполняется **до** извлечения набора опубликованных путей. Удаление и усечение закоммиченного журнала также не проходят проверку.

**Явно отзываю прежнее возражение к DB-only операциям как выходящее за согласованный контракт.** Операции проектов и словаря статусов не обязаны проверять журнал или зависеть от context/Git. Переименование словарного статуса не является переходом заявки. Сохранение SQL-изменения status/title при последующем отказе журнальной фазы соответствует заданному порядку и не доказывает обход файлового барьера. Создание `source.md` до барьера тоже само по себе не является коммитом.

    Что не проверено

    • не подтверждено локально автоматическое переключение интерактивных элементов отчёта в Chromium: первая попытка single-process завершилась сбоем, вторая — ограниченным deadline. Лимиты не повышались. Снимок страницы Derive проверяется отдельно и не подменяет проверку кликов.
    • не проверено настоящий GitHub-hosted Ubuntu job: user systemd, AppArmor, cgroup и результат для конкретного head SHA.
    • не обеспечено независимая идентичность обязательной проверки и отказ поддельному одноимённому check.
    • не выполнялось личная миграция, bootstrap личного home и сетевой sync.
    • не проверено другие ОС, физическая потеря питания, большие длительные истории и p95 производительности. SIGKILL не равен отключению питания.
    • не обещается защита от владельца машины, который напрямую переписывает БД/историю Git, или от администратора GitHub, снимающего правила.
