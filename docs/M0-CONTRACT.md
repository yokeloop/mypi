## 1. Принятые решения и их основание

Ответы инженера заменяют прежние рекомендации агента. Нельзя трактовать их как согласие с файловым lifecycle, обязательной ручной приёмкой или агентным workflow в первой поставке.

### Q1 — состояния в БД с самого начала

Исходный ответ:

> Q1 - несколько устройств не нужны в начале, но я бы сразу заложил хранение состояний в базе данных а не в MD файлах. Я хочу получить больше детерменированности, я не хочу держать весь прогресс работы внутри md файлов. MD файлы - для контекста работы агентов

**Принято:** первая версия локальная, без multi-device; БД — источник истины для управляемого состояния. Markdown — контекст и знания агентов, не оперативные карточки прогресса.

**Следствия:**

- Нет промежуточного этапа request lifecycle в Markdown и последующего переноса статусов в БД.
- БД не disposable cache и не проекция frontmatter. Потеря БД требует восстановления БД, а не парсинга journal.
- Ограничения, транзакции, допустимые изменения и проверки ревизий обеспечиваются кодом и БД; одна лишь установка SQL-движка не делает поведение детерминированным.
- Приёмка результата LLM не становится математически детерминированной; детерминированными должны быть правила обработки её результата и изменения состояния.
- БД не означает PostgreSQL, сервер или облако. Конкретный движок ещё не выбран инженером; для одной машины рекомендуется SQLite.

### Q2 — обычная работа без учёта

Исходный ответ:

> Q2 - нет, обычная работа разрешена без учета

**Принято:** сообщения и обычная работа в чате не создают request автоматически. Capture и управляемый учёт — явные действия; tracker не обязателен. Это не запрещает записывать реальные исходы в память/journal по действующим правилам.

### Q3 — правила приёмки определяет unit

Исходный ответ:

> Q3 - не обязательно. Это определяется выбранным флоу и набором агентов. Условия кто принимает результат живут на уровне сабагента внутри brick

**Принято:** нет глобального требования «только инженер переводит в done» и обязательного отдельного reviewer для любого сценария. Правила приёмки находятся в определении соответствующего юнита; выбранный flow связывает юниты и их результаты.

**Разделение ответственности будущей системы:**

- **Unit** определяет, что считать принятым результатом и кто/что его принимает: проверки, другой агент, инженер, сочетание условий.
- **Flow** выбирает юниты, связывает шаги и их условия завершения; не вводит вторую противоречащую политику приёмки за юнит.
- **Runtime** проверяет контракт результата, полномочия и выполнение объявленных условий; фиксирует переход в БД, а не доверяет одной фразе «готово».
- Запрошенное юнитом human approval нельзя заменить exit code 0; автоматическую приёмку не нужно принудительно превращать в ручную.
- Если контракт приёмки отсутствует/неоднозначен, runtime не угадывает успех. Точная схема контракта — при разработке первого юнита, не в M0.
- Приёмка результата не даёт новых прав на deploy, push, tracker update или выход за scope. Правила внешних записей остаются в силе.

Точный список lifecycle statuses, включая необходимость отдельного `acceptance`, **не фиксируется сейчас глобально**. В первой поставке нет исполнения flow. Прежняя универсальная state machine — отозванная рекомендация, не принятое требование.

### Q4 — общий inbox не включается в scoped warmup

Исходный ответ:

> Q4 - нет

**Принято в контексте вопроса Q4:** org/project warmup не показывает общий inbox и посторонние проекты. Наследуется родительская MEMORY, а не всё содержимое родительских каталогов. Глобальный warmup может показывать общий индекс.

### Q5 — локальный commit автоматически, сеть отдельно

Исходный ответ:

> q5 - Изменяющая CLI-команда делает локальный commit; сетевой sync разрешается отдельно

**Принято:** для изменений файлов памяти локальный commit — часть команды; сетевой sync требует отдельного разрешения. Это не разрешение коммитить движок/рабочие проекты в этой сессии.

Дополнительное подтверждение инженера:

> согласен, базу в git не храним

**Граница Q5 согласована:** БД не хранится в git. Git commit и DB commit — разные операции; история контекста не заменяет сохранение и backup состояния. Для реализации применяется следующее разделение:

| Тип изменения | Устойчивое сохранение |
|---|---|
| MEMORY/note/journal/context и другие версионируемые файлы | Запись + локальный git commit только изменений операции |
| Только состояние/метаданные в БД | DB-транзакция; без пустого git commit и без копирования состояния в Markdown |
| БД + файлы | DB-транзакция и восстановимая файловая операция с git commit; частичное выполнение явно видно |
| Передача данных по сети | Отдельно разрешённый sync; commit не означает, что он выполнен |

БД, WAL/служебные файлы и снимки БД не хранятся в git. Для БД — отдельная процедура backup/restore, не SQL dump в каждом git commit. DB-only команда не обязана создавать искусственный файловый diff или пустой git commit.

Продуктовая граница сохранения закрыта. Точный протокол смешанных операций и backup/restore проектируется и проверяется в M1; согласие не утверждает конкретный механизм или DB-движок.

### Q6 — первая поставка только память и проекты

Исходный ответ:

> q6 - нет, в начале я хочу получить просто систему управления памятью и проектами. Флоу и сабагентов под свои задачи я буду строить поэтапно позже

**Принято:** первый продукт — система управления памятью и проектами. Не минимальный агентный workflow, не обязательный request lifecycle, не один worker/reviewer «для демонстрации архитектуры».

Будущие flow и юниты добавляются по реальным задачам и отдельному запросу. Сейчас нужна граница расширения, а не таблицы всех будущих run/step/lease, DSL или каталог агентов.

### Runtime — Node.js вместо Python

Исходное требование:

> я хочу что бы использовался не python а nodejs

**Принято:** новый CLI, domain core и storage adapters — Node.js. Python остаётся только существующим legacy-прототипом/источником миграции до замены; Node-обёртка над Python не считается выполнением требования.

JS или TypeScript, Node LTS и DB-драйвер выбираются при технической подготовке M1. Node.js — уже принятое требование; TypeScript не приписывается инженеру как отдельно выбранный язык.

## 2. Название блока с сабагентом

Исходное требование:

> мне не нравится термин brick для блоков с сабагентами, надо придумать другой

Решение инженера после выбора однословного названия:

> да давай unit

**Принято: `unit` / «юнит».** Предложение `agent module` заменено выбранным однословным термином. Выбор названия не утверждает config key, manifest filename или имя npm-пакета.

Юнит включает роль/инструкции агента, входной/выходной контракт, ограничения и правила приёмки. Это определение повторно используемого компонента, а не запущенный процесс.

| Термин | Значение |
|---|---|
| Unit / юнит | Определение поведения, интерфейса и приёмки |
| Агент / сабагент | Конкретный исполнитель на основе определения |
| Flow | Связи и порядок исполнения юнитов |
| Runtime | Код, который проверяет и исполняет flow, хранит состояние |
| Pi extension | Исполняемое расширение Pi; не синоним юнита |
| Package | Способ доставки; может содержать несколько юнитов |

Роль — часть юнита; Pi skill и extension — другие механизмы. Термин `unit` в названии unit-тестов по-прежнему означает уровень тестирования, а не юнит агента.

Старые термины остаются только в исходных цитатах, историческом наброске и его стабильном пути. История решений не переписывается; новые API/каталоги при этом не создаются.

## 3. Граница ближайшей реализации

**Входит в M1:** существующие сценарии memory, journal, error, note, capture, project add/list и warmup; Node.js; авторитетное DB-хранилище управляемого состояния; файловый контекст; локальные commits по Q5; миграция legacy-данных, backup/recovery и тесты.

**Не входит:** request workflow, агентный runner, flow DSL, acceptance engine, обязательный tracker, multi-machine, табы, дистрибуция юнитов.

Для M1 предлагается следующая минимальная граница данных:

- В БД — реестр организаций/проектов и структурированная идентичность capture/inbox; состояние операций, если оно необходимо для recovery.
- В Markdown — MEMORY, glossary, notes, journal/errors и другие контекстные артефакты; source capture остаётся исходным текстом и может быть отдан агенту как контекст без хранения его жизненного цикла в MD.
- Точное размещение source capture выбирается с форматом миграции: один канонический исходник, не две независимо редактируемые копии.
- Будущие request/run/step/attempt, статусы и результаты приёмки — в БД, **когда появится соответствующая функция**, а не все таблицы заранее.
- Паспорт `projects.json` и прежний inbox — legacy-вход миграции, не вечный параллельный источник истины.

Это техническое предложение для реализации принятых границ, не утверждённая SQL-схема. Оно не требует выдумывать пользовательские поля, которые агент может выяснить при действии.
