Предложение: добавить локальный MCP-сервер с 31 предметным инструментом: 30 операций существующего CLI и один помощник определения проекта по папке. MCP — Model Context Protocol, протокол вызова инструментов агентом.

Код — в том же репозитории и pnpm-пакете, рядом с CLI. Оба входа используют общие сценарии, БД и Git контекста. Pi сам запускает процесс по настройке MCP; отдельный постоянно работающий сервис не нужен.

Решения инженера: в комментариях Derive v2 подтверждены общий API и каталог, пользовательское подключение во всех сессиях и штатный MCP + инструкция без управления сессиями. Последующим запросом удалён legacy: в каталоге теперь 31 инструмент, без import_legacy. Сейчас подготовлен только план — без установки зависимостей, изменения Pi или личного хранилища.

Цель

Ты работаешь в обычной сессии агента и просишь: «подними контекст проекта», «запиши результат», «создай задачу», «покажи историю». Агент вызывает конкретный MCP-инструмент со структурированными аргументами, а не собирает shell-команду и не угадывает флаги.

Сохраняются все принятые правила: SQLite — источник состояния; home/ — отдельный Git; журнал общий и append-only; source неизменяемый; request необязателен; запись не запускает исполнение задачи.

Не входит: HTTP, OAuth, удалённый доступ, отдельный daemon, новый tracker, таблица сессий, перенос истории Pi в mypi, flow, сабагенты, автозапуск LLM, синхронизация по сети. Для чтения контекста достаточно инструментов — отдельные MCP resources/prompts в первой версии не нужны.

Какие инструменты будут — полный каталог

Названия ниже — имена сервера. В Pi они получат префикс mcp__mypi__, например mcp__mypi__request_create. Каждая операция — самостоятельный инструмент; run_command, произвольных SQL и shell нет.

Обозначения: ? — необязательный аргумент; ContextScope — global/org/project; Scope добавляет request. Scope передаётся объектом {type,key?}, например {"type":"project","key":"MP"}. Для чтения всего журнала есть отдельное явное значение "all". Это не новый DB-формат: приложение разрешает ссылки через существующий реестр.

В scoped-инструментах scope обязателен, в том числе {"type":"global"}: забытый проект не должен тихо превращаться в глобальную запись. Capture явно относится к общему inbox. У request_create проект указан явно: org/project либо null для REQ. Не вводим сохранённый «текущий проект» сервера.

TextInput — ровно один из вариантов {text:string} или {file:absolutePath}. Это замена позиционного текста / CLI --file, без временных файлов для обычных сообщений. Внешние пути в MCP задаются абсолютными; пути внутри контекста — относительно home, артефакты progress — относительно папки задачи.

Как именно будет реализовано

  1. Типизированный вход. src/app/commands.ts станет discriminated union команд с предметными полями вместо универсальных строк args/options. CLI разбирает argv, MCP проверяет строгую JSON Schema (неизвестные поля отклоняются, а не удаляются валидатором); оба передают одинаковые команды в executeCommand. Синтаксис и JSON-ответы существующего CLI сохраняются.
  2. Один владелец правил. Диспетчер вызывает текущие createApp/createWorkspace и системные сценарии. MCP не обращается к таблицам, Git или файлам напрямую. Существующие бизнес-проверки не заменяются схемами протокола.
  3. Небольшое расширение определения проекта. project_resolve канонизирует переданную папку и ищет зарегистрированный checkout, равный ей или являющийся её родителем по границам компонентов пути. При вложенных checkout выбирается наиболее глубокий; при нескольких равных кандидатах — неоднозначность, не первый в списке. Проект без checkout выбирают явно по identity. Правило располагается в projects с существующим портом путей, не в MCP.
  4. Официальный SDK. Предлагаются @modelcontextprotocol/sdk@1.32.0 и zod@4.6.5, проверенные пока только по метаданным и документации. McpServer, StdioServerTransport, registerTool; Zod — схемы входа/выхода на границе. Не импортировать HTTP-server entrypoints. Наличие транзитивных HTTP-зависимостей SDK не означает запуск HTTP; их состав и стоимость отдельно проверяются.
  5. Без побочных эффектов загрузки. Только main.ts подключает stdin/stdout. Импорт server/tools не запускает процесс, не открывает DB и не создаёт home. Инициализация MCP и tools/list доступны до bootstrap.
  6. Ресурсы на один вызов. Приложение открывается для операции и закрывается в finally. Нет вечного DB-handle, устаревающего после restore. DB-only проекты/справочник не приобретают зависимости от наличия Git.

Ответы, ошибки и отмена

У инструментов будут inputSchema и outputSchema. Для программного вызова — structuredContent; текстовый content содержит тот же сериализованный результат, чтобы клиент без structuredContent не терял поля. Успех: {status:"ok", data:...}. Обычная ошибка: isError:true и {status:"error", message:...}. Частичный исход переносит существующий PartialError без потери полей:

{
  "isError": true,
  "structuredContent": {
    "status": "partial",
    "message": "...",
    "saved": ["..."],
    "missing": ["..."],
    "paths": ["..."],
    "requestId": 17
  },
  "content": [{"type": "text", "text": "тот же JSON"}]
}

Это схема ответа, не запись реально выполненной операции; requestId передаётся только если известен. В saved/missing — факты из core, не предположения MCP. Ошибка не всегда означает отсутствие записи. Некорректные параметры/неизвестный инструмент отклоняются до вызова сценария.

Сервер не повторяет мутации автоматически. Потеря соединения или клиентский timeout после начала вызова означает неизвестный клиенту исход, а не rollback. Сначала сверка карточки, журнала, файлов и Git; затем явное завершение partial. JSON-RPC request ID — корреляция ответа, не ключ идемпотентности.

В одном серверном процессе инструменты исполняются последовательно, включая async backup; достаточно небольшой последовательной цепочки Promise, не нового supervisor или постоянной очереди. Отменённый ожидающий вызов не начинает работу. Уже начатую синхронную SQLite/Git-операцию нельзя обещать мгновенно прервать с откатом. При закрытии stdin/SIGTERM перестаём принимать новые вызовы и освобождаем ресурсы; принудительный kill оставляет тот же контракт partial/сверки.

Несколько сессий имеют отдельные процессы MCP, но одну БД и home. Согласование записей между ними остаётся в общих транзакциях/блокировках M1, действующих также для CLI. Локальная цепочка MCP не выдаётся за межпроцессную защиту. Bootstrap/restore — режим обслуживания: до него остановить другие писатели; никакого нового глобального recovery/lock engine.

Безопасность и объём ответов

  • Предлагается зарегистрировать 31 инструмент. Административные действия имеют отдельные имена и предупреждения: bootstrap/restore запускаются по прямому намерению инженера; context_commit/restore/touch — после сверки. Не вводим глобальное подтверждение каждой обычной записи.
  • readOnlyHint/destructiveHint/idempotentHint/openWorldHint описывают реальные свойства. Запись журнала/capture/progress не объявляется идемпотентной; backup не объявляется чтением. Аннотации, инструкции и скрытие инструмента — не защита доступа и не доказательство подтверждения человеком.
  • Локальный сервер работает с правами пользователя и может обслуживать разные зарегистрированные проекты. Scope фильтрует данные, но не является ACL. Клиенту MCP не выдаётся обещание изоляции одного проекта от другого.
  • Нет произвольных shell/SQL-команд; Git остаётся внутри существующего адаптера. Context-пути ограничены home. Явные file/backup/checkout аргументы могут обращаться к другим разрешённым пользователю локальным путям — это не sandbox файловой системы.
  • Текст source передаётся без trim, шаблонного заголовка или потери BOM/CRLF. Неизвестные поля и неверные типы не исправляются молча. Статусы проверяются по БД, не статическим enum.
  • Сервер не обрезает содержимое молча и не вводит новый SQL-индекс журнала. Используем существующие from/to/type/limit. Pi может сократить длинный текст для модели и сохранить полный ответ во временный файл; codemode получает полный MCP-результат. Эта особенность клиента не даёт права считать сокращённый текст всей историей.
  • Stdout — только протокол. Диагностика — stderr, без полного исходника задачи/секретов. Нет автоматического журнала каждой MCP-команды: рабочий journal хранит исходы, не технический трафик.

Как будет запускаться

После реализации: обычная сборка mise exec -- pnpm build создаёт второй entrypoint. Его можно запустить из корня командой mise exec -- node dist/src/mcp/main.js; он ждёт протокол, а не печатает интерактивное меню. В package.json появится bin mypi-mcp, но глобальная установка не требуется.

Для подключения рекомендуются абсолютные пути к Node 24 и собранному entrypoint. Не запускать через shell-строку, npx с загрузкой пакета или команду сборки при каждом открытии сессии. Pi создаёт дочерний процесс сам; порта и постоянно работающего systemd-сервиса нет.

Данные определяются местом установленного движка и действующим XDG-путём БД, не cwd MCP-клиента. home/ остаётся внутри клона; настройку переноса home не добавляем. Для конкретной машины сейчас известны такие пути:

{
  "mcpServers": {
    "mypi": {
      "command": "/home/priney/.local/share/mise/installs/node/24.21.0/bin/node",
      "args": ["/home/priney/Projects/mypi/dist/src/mcp/main.js"],
      "description": "Память, проекты, журнал и задачи mypi. Определи проект через project_resolve, затем warmup; записывай фактические результаты в явный scope.",
      "exposure": "codemode",
      "toolExposure": {
        "project_resolve": "direct",
        "warmup": "direct"
      }
    }
  }
}

Это пример добавляемой записи, не замена текущего mcp.json. На другой машине пути получают из её установки, например через mise which node; пути Павла не встраиваются в продукт. Нестандартный XDG_STATE_HOME при необходимости передаётся клиентом так же, как CLI, без нового mypi-конфига.

Почему 2 direct и остальные codemode: агент сразу видит как определить проект и поднять память, но не получает 31 полную схему в каждом запросе модели. Остальные инструменты доступны через поиск/описание и вызов codemode. В другом MCP-клиенте формат exposure может отсутствовать — это настройка Pi, не требование сервера.

Одноразовая настройка по документации Pi: pi mcp add mypi --exposure codemode -- /absolute/node24 /absolute/mypi/dist/src/mcp/main.js, затем точечное добавление двух toolExposure и description. Предпочтительно пользовательский ~/.pi/agent/mcp.json; если изменён agent-dir, используется его фактический путь. Проектный вариант .pi/mcp.json потребует project trust и будет доступен только соответствующему проекту.

Диагностика: pi mcp list вне сессии; /mcp внутри. Для уже открытой сессии после внешней правки — /reload; при разрыве — /mcp reconnect mypi. pi mcp list обращается также к другим включённым серверам, поэтому протокольные тесты выполняются в отдельном временном профиле с одним mypi. Перезапуск после обновления сборки обязателен: уже запущенный Node-процесс сам новый JS не подхватывает.

Как MCP подключается к сессиям — и чего не делает

Подключение инструментов и привязка работы к проекту — разные вещи. Pi читает mcp.json при старте сессии и соединяется с сервером. MCP не получает автоматически всю переписку, постоянный Pi session ID или выбранную задачу. Поэтому server-процесс не является записью сессии в mypi.

СитуацияПредлагаемое поведение
Новый разговор в checkout проектаАгент берёт рабочую папку из контекста сессии и передаёт её в project_resolve. При однозначном результате вызывает warmup с возвращённым project scope. Server cwd для этого не используется.
Проект задан словами или не имеет checkoutАгент использует явный org/project, при необходимости читает реестр. Не придумывает соответствие папки проекту и не создаёт паспорт автоматически.
Продолжение задачиАгент вызывает request_show, journal_read нужного request scope и context_read по нужным путям. Текущий статус берёт из БД, а не из старого текста разговора.
Работа без задачиДопустима. Результат сохраняется через journal_add в scope проекта. При работе по задаче — request_progress; тот же исход второй раз в project journal не дублируется, он уже виден через scoped выборку.
Возобновление / новая ветка разговораПодключение инструментов выполняет клиент. Агент заново сверяет проект/задачу и актуальное состояние. Движение по дереву разговора не отменяет уже сделанные DB/FS/Git-записи.
Два разговора одновременноДва соединения/процесса используют одну установку; каждый вызов имеет явный scope/key. Нет общего mutable currentProject/currentRequest. Проверяются коллизии и блокировки с CLI.
Разговор закрыт или аварийно оборванPi останавливает stdio-процесс. Сервер не выдумывает «итог сессии» из shutdown. Реальные исходы записываются по мере работы; неизвестный результат последнего вызова требует сверки.

Инструкция агенту из integrations/pi/mypi-instructions.md добавляется отдельным отмеченным фрагментом в реально применяемый пользовательский файл контекста Pi. Существующие инструкции сохраняются; учитывается приоритет AGENTS.override.md. Этот фрагмент объясняет выбор scope, warmup, чтение полных артефактов, необязательность request и запрет слепого retry. Создавать extension только ради регистрации MCP не нужно.

Это поведение агента по инструкции, не механический lifecycle-hook. Если нужен гарантированный вызов warmup на событии старта, индикатор выбранного проекта, сохранённая связь Pi-session → request или автозапись при завершении — потребуется отдельное согласование интеграции Pi. В этом плане нет tools session_start/session_close и новой таблицы sessions.

Пример рабочего цикла после реализации

project_resolve({path: "/work/acme/api"})
  → проект acme/api, code API, scope {type:"project",key:"API"}

warmup({scope:{type:"project",key:"API"}})
  → память и индекс; затем context_read для нужных полных материалов

request_create({
  project:"acme/api", title:"Разобрать ошибку чтения",
  status:"research", slug:"read-error",
  source:{text:"точная исходная формулировка"}
})
  → карточка API-1

request_progress({
  key:"API-1", text:"Причина воспроизведена; сохранён разбор",
  artifacts:[{path:"research/result-v1.md",text:"проверенные детали"}]
})

# В другом разговоре:
request_show({key:"API-1"})
journal_read({scope:{type:"request",key:"API-1"},limit:10})
context_read({path:"projects/acme/api/requests/API-1-read-error/research/result-v1.md"})

Пример синтетический. Номер возвращает БД; сервер не обещает всегда API-1. Статус research используется только если он есть в текущем справочнике. Регистрация проекта и личный bootstrap не выполнялись этим документом.

Проверки

Ниже — ожидаемые проверки после реализации, не утверждение об уже пройденных тестах MCP. Единый источник политики — docs/TESTING.md. Бюджеты не повышаются: fast ≤5 с; admission+fast+boundary ≤30 с; внешний deadline с cleanup 60 с; 2 CPU, 1 GiB, 64 tasks, один worker/run. Install и build считаются отдельно.

Исходная публикация v2 сверена по SHA256 и top/full render. Эта версия обновляет каталог после прямого запроса удалить legacy; проверка публикации фиксируется в docs/evidence/mcp-plan-publication.txt.

Откат

  1. Подключение Pi: до изменения сохранить прежний пользовательский конфиг/инструкции локально с исходными правами, без публикации секретов. Удалить только запись mypi (pi mcp remove mypi для стандартного user-level случая) и добавленный фрагмент инструкции, затем /reload. Остальные серверы и настройки не трогать.
  2. Сервер: остановить активные соединения через клиент. Старые CLI и данные продолжают существовать; удаление MCP-настройки не удаляет БД или home.
  3. Код/зависимости: вернуть коммиты адаптера и рефакторинга через обычный Git revert, восстановить согласованный lockfile, выполнить frozen install и build. Обновления проверяющих правил возвращать вместе с соответствующим кодом, а не оставлять ослабленную проверку.
  4. Данные: миграции SQL и нового layout этим планом не предусматриваются. Если во время разрешённой эксплуатации были записи, откат программы не откатывает их автоматически. Состояния до и после изменения сверяются; mutable-контекст восстанавливается штатной командой, неизменяемая история не переписывается. Полное восстановление — из проверенной резервной копии в отсутствующее состояние, без уничтожения текущего.

Решения инженера

Ответы получены в комментариях Derive к v2 и зафиксированы ниже. Повторно отвечать не нужно; реализация MCP и изменение личной установки этой очисткой не запускаются.

1. Подтверди: один локальный stdio MCP в том же пакете, общий типизированный API с CLI и весь каталог из 31 инструмента, включая явно названные операции обслуживания.
   Сейчас: предложены src/mcp, небольшой общий рефакторинг app/cli и один новый lookup проекта по checkout; SDK 1.32.0 + Zod 4.6.5 ещё предстоит проверить в сборке.
   Ответ: «Подтверждаю» (Derive v2). Каталог сокращён до 31 после запроса удалить legacy.

2. Реши: подключение а) пользовательское — во всех твоих сессиях, б) только в выбранных проектах?
   Сейчас: рекомендую а), с project_resolve и warmup как direct, остальными через codemode. Все операции используют явный scope/key, не общий текущий проект.
   Ответ: «а)» (Derive v2): пользовательское подключение.

3. Реши: для первой версии а) штатное MCP-подключение Pi + инструкция агенту, без управления сессиями, б) сначала дополнить план обязательными lifecycle-возможностями?
   Сейчас: рекомендую а). Вариант а) не обещает автоматический warmup по событию, session → request registry или автоматическую итоговую запись при закрытии.
   Ответ: «а)» (Derive v2): MCP + инструкция, без управления сессиями.
