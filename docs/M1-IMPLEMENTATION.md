## Разрешение и граница

2026-10-02 — инженер ответил «начинай»: реализация M1 разрешена. Это не разрешение переносить личные данные, создавать home, коммитить движок/проекты или выполнять сетевой sync.

Начата реализация принятого стека, схемы БД и вертикального пути регистрации/чтения проектов через Node API и CLI. Проверки выполняются только на временных данных. Это ещё не готовность всей M1: requests, контекст/Git, memory, warmup, import и backup/restore остаются в работе по PLAN.

Архитектурный контракт — [M1-START.md](M1-START.md); лимиты и admission — [TESTING.md](TESTING.md).

## Реализовано

- Один ESM-пакет: Node 24.21.0, pnpm 12.6.0, TypeScript 5.9.3 strict, better-sqlite3 13.0.3; проверенный встроенный SQLite — 3.53.4. Версии зафиксированы в mise/package/lockfile, глобальный Node 26 не заменён.
- [Начальная SQL-миграция](../src/infrastructure/database/migrations/001-initial.sql): четыре STRICT-таблицы, FK/unique/check, отдельная уникальность REQ-номеров. user_version и миграция в BEGIN IMMEDIATE; seed не перезаписывает изменённые статусы. Используемый статус не меняет терминальность, проект с запросами — code; сохранённые requests не удаляются.
- [Проектный API](../src/modules/projects/public.ts): add/list и разрешение зарегистрированного global/org/project scope. SQL — в адаптере модуля, сборка зависимостей — в app. Добавление организации/проекта транзакционно; конфликт не оставляет лишнюю организацию. Slug сегмента: `[a-z0-9]+(?:[._-][a-z0-9]+)*`; checkout опционален и проверяется как существующий каталог.
- CLI: `db init`, `project add <org/project> --code CODE [--path directory]`, `project list [--org org]`, `--help`. JSON на выходе; ошибка — stderr и ненулевой exit. Это DB-only операции, без home/Git/сети и без Python backend. Python использовался только штатным node-gyp при установке native-зависимости.
- XDG/default path вне движка/контекста, с проверкой symlink-алиасов. Защита действует и при входе через app API. Чтение открывает существующую БД readonly, не инициализирует её и не меняет файл. Подключение личных данных пока не выполнялось.

## Проверки и их стоимость

Первый набор — **7 fast + 1 boundary**, без тестов будущих функций. Fast защищает DB constraints/seed, проектные scope/rollback, пути и разбор CLI через API. Boundary проверяет настоящий launcher и сохранение→чтение между независимыми процессами: этого не доказывает внутрипроцессный тест. Полную матрицу через subprocess не повторяли.

Выполнены `pnpm install --frozen-lockfile`, `pnpm build`, `pnpm verify` и `pnpm test` под Node 24. Команды и фактические stdout/stderr, включая ожидаемые отказы, — [evidence/m1-initial-checks.txt](evidence/m1-initial-checks.txt).

Последний verify: 8/8, service runtime **1.120 s**, cgroup memory peak **319 MiB**, tasks peak **24**. Отдельный fast: 7/7, service runtime **0.855 s**, memory peak **322.3 MiB**, tasks peak **11**. Это вся ограниченная группа, включая setup/admission и файловый cache, не RSS одного worker. Несколько успешных verify дали примерно 1.1 s; это не статистический baseline/p95 и не оценка стоимости всей M1. До изменений Node-набора не было, сравнимого base-прогона нет; HEAD остался `9b68f281eb26d66dad37a58c750aba31bc1e4d2b`.

В одноразовой копии проверены отказы:

- Удаление org-фильтра вызвало нужный assertion о чужом проекте; исходная версия прошла. Это доказательство чувствительности, не тест поломанного setup.
- Неизвестный профиль, skip и child_process в транзитивном fast-helper отклонены до тестов.
- node:fs в предметном API отклонён архитектурной проверкой, включая нормализацию builtin-имён dependency-cruiser.
- Изменённые входы после build отклонены как stale build; проверяются также хеши собранных файлов.
- Оставленный boundary-тестом потомок привёл к ненулевому результату, хотя test runner был зелёным; PID namespace уничтожен.
- Безопасная ожидающая fixture остановлена systemd по ужесточённому deadline 1 s. Runtime directory удалён и unit неактивен; не применялись реальные resource-exhaustion нагрузки.

## Реальная граница ограничения

`test` и `verify` используют один фиксированный systemd user unit: одновременный второй запуск не создаёт независимую квоту. CPU/RAM/tasks и остановка принадлежат systemd/cgroup, cleanup runtime directory — systemd. Bubblewrap создаёт отдельные PID/network namespaces; внутри — временная копия кода/зависимостей readonly, отдельные home/tmp и очищенное окружение. Личного home, рабочих checkout, credentials и пользовательского Git config нет. Без этих средств запуск завершается ошибкой, fallback на неограниченный runner отсутствует.

Fast использует Node permission mode без child-process/worker permissions; native addon разрешён для SQLite. Поэтому Node permissions **не объявляются полной sandbox-защитой**: фактическая внешняя изоляция — bubblewrap/cgroup. Полные FS permissions внутри изолированной среды нужны для symlink fixtures; исходники/зависимости остаются readonly средствами ОС.

Dependency-cruiser проверяет направления/циклы/публичные границы. Маленький admission дополняет discovery, skip/динамические эффекты и достижимые зависимости. Это не доказательство отсутствия любых динамических эффектов. Независимого review, доверенного неизменяемого gate и CI пока нет: агент с правом менять scripts может изменить проверки. Self-bypass технически не закрыт; это остаётся условием последующей приёмки, не обещанием текущей версии.

## Исправленные проблемы настройки

- TypeScript 7.0.2 не предоставил ожидаемый compiler API для admission; до завершения выбран совместимый 5.9.3, lockfile обновлён.
- Node permissions отклонили создание symlink с частичными FS permissions; разрешены FS-операции только внутри внешней OS-изоляции, её границы не расширялись.
- Первый прогон мутации не дошёл до тестов: pnpm в неполной временной копии попытался автоматически переустановить зависимости и отклонил install script. Такой отказ не засчитан чувствительностью. Следующие проверки использовали готовую копию зависимостей и прямой запуск закреплённого tsc; установка из build больше не вызывается.
