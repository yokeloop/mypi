## Ключевая развилка

Pi навязывает одно разделение сам: **расширения — это код с полными правами
системы, агенты — это данные**. Поэтому обмен между людьми должен происходить
в слое данных; код — один и тот же для всех.

## Три артефакта, строго разделённых

| Артефакт | Формат | Кто автор | Сколько экземпляров |
|---|---|---|---|
| **Кирпич** (сабагент-плагин) | agent.md + contract.yaml + config.yaml | любой человек | много, обмениваются |
| **Флоу** | flow.yaml (данные) | владелец проекта | по одному на скоуп |
| **Оркестратор** | extension (код) | мы, один раз | один движок |

Правило: **кирпичи и флоу — данные, код — только движок**. Чужой кирпич нельзя
заставить выполнить произвольный код; кодовые кирпичи — отдельный класс доверия.

## 1. Кирпич — единица обмена

```
brick-<name>/
├── brick.yaml     # манифест: name, version, author, role-slot, requires, code: false
├── agent.md       # роль: frontmatter (tools, model, guards) + system prompt
├── contract.yaml  # вход/выход — типизированный интерфейс
├── config.yaml    # сейфгарды, permission, acceptance (уровень плагина)
└── scripts/       # вспомогательные скрипты
```

### Contract — ключ к совместимости чужих кирпичей

```yaml
input:
  required: [goal, request_file]
output:
  required: [status, report_path]
```

Оркестратор валидирует стыковку **при компиляции флоу**: output кирпича A
⊆ input кирпича B, иначе флоу не собирается. Договорённость между людьми
вынесена в схему — люди пишут кирпичи независимо друг от друга.

### Два класса доверия

- **Декларативный** (agent.md + config, без своего кода) — обмен свободный.
  Гварды встроены в формат: `permission: {edit: ask}`, `allowedAgents`,
  `acceptance`, launch rules — всё уже в pi-subagents, enforcement технический,
  не промптовый.
- **Кодовый** (`code: true`, добавляет свой extension.ts со своими турами) —
  требует ревью или сендбокса (контейнер, фаза 5): extension = полные права
  системы.

### Role-слоты — полиморфизм обмена

Стандартизуем слоты: `scout / worker / reviewer / oracle / orchestrator`
(готовая классификация из доки pi-subagents). Флоу ссылается на слот,
конкретный кирпич подставляется конфигом проекта. Мой reviewer и твой reviewer
взаимозаменяемы, если контракт совпадает.

## 2. Флоу — данные проекта

`home/<org>/<project>/flow.yaml`, синк через git home/, каскад по скоупам
(project наследует org, org — root — та же семантика, что warmup):

```yaml
states: [backlog, planning, doing, review, deploying, done]   # lifecycle из ADR-0001

doing:
  steps:
    - brick: scout@1.x
      input: {goal: "{request.goal}"}
    - brick: worker
      input: {brief: "{previous.report}"}
    - brick: reviewer
      fresh: true                    # независимый взгляд
  rules:
    - if: {reviewer.findings: high}
      goto: doing
    - if: {reviewer.findings: ok}
      goto: deploying

review:
  parallel: [security-reviewer, code-reviewer]

escalation:
  - on: [timeout, acceptance_failed]
    action: notify_engineer          # человек-как-шина (ADR-0003)
```

Флоу отвечает на исходный пункт 4 идеи: «связывает статус задачи и сабагента,
который за статус отвечает; массив и луп сабагентов; правила перехода».
Сейфгарды и условия запуска — в конфиге кирпича («на уровне плагина»).

## 3. Оркестратор — единственный код

Extension `mypi-orchestrator` в движке, четыре блока:

1. **Компилятор флоу**: flow.yaml → dispatch-план (ADR-0002), валидация
   контрактов, резолв слотов.
2. **Status hook**: смена статуса request → запуск секции флоу (склейка
   с ADR-0001 — lifecycle в файлах).
3. **Диспетчер**: spawn через pi-subagents с enforcement: allowedAgents-каскад
   (оркестратор проекта поднимает только кирпичи своего флоу), права `tools`
   — из ADR-0003.
4. **Аудит**: авто-запись исхода в journal/errors при каждом переходе —
   «журнал ошибок = источник багрепортов» становится бесплатным следствием.

### Два слоя управления (по NorthStar-модели)

- **Детерминированное** (steps, rules) исполняет интерпретатор — без
  LLM-решений, дёшево и предсказуемо.
- **Недетерминированное** (вопросы инженеру, приёмка, неоднозначная
  маршрутизация) — оркестратор-**агент**, тоже кирпич (слот `orchestrator`,
  с правом dispatch в tools). Живёт в табе на задачу — исходная картина
  «каждый пайплайн — отдельный таб». Движок — его инструментарий, не замена.

## 4. Обмен между людьми

- Дистрибуция — готовые **pi packages**: `pi install npm:@author/brick-reviewer`
  или `git:...`. Реестр = npm/git; brick.yaml — витрина (описание, слот,
  совместимость).
- Версионирование: semver; breaking change в contract.yaml = major.
  В флоу — пины `scout@1.x` (float в рамках major).
- org-уровень — общая библиотека кирпичей организации; user-уровень — личные.

---

## Готово в Pi vs пишем сами

**Готово** (не пишем): spawn + гварды + allowedAgents + acceptance + модели
(pi-subagents); события/туры/UI/extensions API; дистрибуция (packages);
nested-дерево (AbortSignal-ownership из ADR-0003).

**Пишем сами, три вещи**:
1. Формат кирпича (обёртка над agent.md + contract).
2. Компилятор флоу + status hook (один extension).
3. Конвенция слотов.
