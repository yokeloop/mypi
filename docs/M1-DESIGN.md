## 1. Принято: pnpm

Исходное дополнение инженера:

> дополнение - должны пользоваться pnpm

Для новой реализации используем pnpm, не npm как package manager. Версии и `pnpm-lock.yaml` зафиксированы после отдельного разрешения реализации; установка — с frozen lockfile. CI ещё не настроен; локальная совместимость проверена (M1-IMPLEMENTATION).

Само уточнение про pnpm не утверждало остальной стек; его последующее принятие зафиксировано отдельно в §11. pnpm не требует monorepo/workspaces.

## 2. Какую проблему решаем

Нужно разделение по предметным областям и назначению, а не один большой файл с последовательностью функций. Простое разнесение по `services/`, `repositories/`, `utils/` само по себе этого не обеспечивает: файл уменьшается, но логические зависимости остаются запутанными.

Критерий: изменение одного поведения обычно затрагивает один предметный модуль и его тесты; инфраструктурные детали не проникают в правила, а CLI не становится местом бизнес-логики. Небольшие файлы — следствие связности, не самоцель.

## 3. Варианты и применимость

Эти концепции отвечают на разные вопросы и могут сочетаться. DDD — подход к моделированию, modular monolith — форма системы, Hexagonal — правило зависимостей, Vertical Slice — способ группировки сценариев.

| Концепция | Что даёт | Риск для mypi | Вывод |
|---|---|---|---|
| Глобальная слоистая архитектура: controllers/services/repositories | Простая техническая классификация | Одна функция размазана по всему проекту; общие services превращаются в большие файлы | Слои полезны внутри модуля, не как единственная организация всего проекта |
| DDD | Границы моделей, единый язык, инварианты и ответственность за данные | Формальные aggregates/entities/domain events для простого хранения создадут лишний код | Брать предметные границы и инварианты; богатую модель вводить только там, где есть сложное поведение |
| Hexagonal / Ports & Adapters; близкие идеи Clean Architecture | Отделение правил от CLI, SQL, filesystem и Git; дешёвые проверки правил | Интерфейс на каждую функцию, четыре слоя forwarding и DI framework | Небольшие порты на реальных границах эффектов; не полная церемониальная Clean Architecture |
| Vertical Slice | Код сценария находится рядом: add-project, remove-memory, capture | Каждый сценарий может завести свой SQL/commit/валидацию | Использовать внутри предметных модулей; общие инварианты и механизмы сохранять в одном месте |
| Modular Monolith | Один пакет и процесс исполнения CLI, но явные внутренние границы | Без контроля импортов остаётся лишь набор папок | Лучший масштаб для локальной M1; границы проверяются инструментами |
| Microservices / event-driven система | Независимые deployment и масштабирование | Сеть, брокер, distributed transactions, сложная диагностика без потребности | Для M1 не нужны; доменная изоляция не требует отдельных процессов |

**Выбрано: модульный монолит по предметным областям + Ports & Adapters на границах эффектов + сценарии внутри модулей.** Из DDD берём язык и инварианты, а не обязательный набор классов. Внутри — по возможности чистые функции для решений и небольшой слой исполнения эффектов.

Не добавляем event bus, CQRS-фреймворк, event sourcing, универсальный repository, DI container или плагины ради структуры. Разделить read/write функции можно без отдельной инфраструктуры CQRS.

## 4. Принятые предметные границы M1

Это начальные границы модулей, не заявление, что найдены независимые DDD bounded contexts. `requests` добавлен по уточнению M1 от 2026-10-01. Близкие области могут разделять язык и простые типы.

| Модуль | Ответственность | Не отвечает за |
|---|---|---|
| `projects` | Реестр, identity организации/проекта, локальная привязка checkout, разрешение зарегистрированного scope | Чтение и форматирование MEMORY, запуск работы в проекте |
| `memory` | Факты global/org/project, добавление/удаление, наследование родительской памяти | Паспорт проектов, stdout, автоматический capture |
| `knowledge` | Journal, errors, notes и чтение адресуемого проектного контекста; правила исходов и no-overwrite | Очередь задач и lifecycle; не универсальный менеджер всех файлов |
| `inbox` | Явный capture, сохранность source и чтение inbox; отдельная таблица captures не вводится | Автоматическое создание request или запуск flow |
| `requests` | Учёт запросов, DB-состояние, владение справочником request_statuses и API ведения прогресса; принятая связь с папкой контекста — context_dir по M1-REQUESTS | Исполнение flow, запуски сабагентов и универсальная история технических операций |

`journal`, `errors` и `notes` — отдельные сценарии/подобласти внутри knowledge, а не один большой `knowledge-service.ts`. Их физический механизм записи может быть общим, но правила и формат различаются. Для истории запросов выбран общий JSONL-reader/writer с ротацией; разрешение scope по DB-связям координируется через публичные API владельцев данных. CLI и будущие входы используют один reader, не отдельные реализации фильтрации.

**Warmup — составной read-only сценарий приложения, не отдельная доменная сущность.** Он вызывает публичные API модулей, применяет контракт выбранного scope и собирает результат; не читает их таблицы и файлы напрямую.

**Bootstrap, backup и recovery — системные сценарии приложения.** Их координация не должна попадать в CLI, один гигантский `storage.ts` или универсальный runner. Обработка конкретного сбоя выбирается для реальной команды; это не основание заранее строить универсальный recovery engine или таблицы операций.

## 5. Принятая организация каталогов

Расширение `.ts` соответствует выбранному TypeScript (§11). Приняты ответственность каталогов и модульные границы; конкретные файлы дерева — ориентир. Пустые модули/слои заранее не создаются.

```text
mypi/
├── src/
│   ├── cli/
│   │   ├── main.ts                   # argv, exit, запуск приложения
│   │   ├── commands/                 # тонкие адаптеры команд
│   │   └── output/                   # stdout/stderr и форматирование
│   ├── app/
│   │   ├── create-app.ts             # явная сборка зависимостей
│   │   ├── warmup.ts                 # координация read-only сценария
│   │   ├── bootstrap.ts
│   │   ├── recovery/                 # только при реальном сценарии; не заготовка engine
│   │   └── backup/                   # согласование DB backup и контекста
│   ├── modules/
│   │   ├── projects/
│   │   │   ├── public.ts             # узкий API, не export *
│   │   │   ├── model.ts              # доменные данные и инварианты
│   │   │   ├── add-project.ts        # сценарий, не CLI handler
│   │   │   ├── list-projects.ts
│   │   │   ├── resolve-scope.ts
│   │   │   ├── ports.ts              # нужные этому модулю эффекты
│   │   │   └── adapters/
│   │   │       └── sqlite-project-store.ts
│   │   ├── memory/
│   │   ├── knowledge/
│   │   ├── inbox/
│   │   └── requests/
│   ├── infrastructure/
│   │   ├── database/                # подключение и запуск SQL-миграций
│   │   │   └── migrations/          # одна упорядоченная схема локальной БД
│   │   ├── filesystem/              # безопасные пути/запись
│   │   └── git/                     # subprocess и операции Git
│   └── shared/
│       └── scope.ts                 # только действительно общие чистые типы
├── test/
│   ├── fast/                        # далее по модулям и app-сценариям
│   ├── boundary/                    # реальные границы по TESTING.md
│   └── support/                     # маленькие helpers, не test framework
├── scripts/                         # технические entrypoints разработки
├── docs/, references/
├── package.json
├── pnpm-lock.yaml
├── dist/                            # результат сборки, не исходники
├── home/                            # отдельный git контекста, не в git движка
└── projects/                        # рабочие клоны, не в git движка

$XDG_STATE_HOME/mypi/                # вне git; fallback: ~/.local/state/mypi/
└── state.sqlite3                    # принятый путь; backup/restore отдельно
```

`sqlite-project-store.ts` иллюстрирует адаптер выбранной SQLite через `better-sqlite3` (§11). Адаптер, знающий смысл project-таблиц, принадлежит projects. Общая инфраструктура знает, как открыть БД, выполнить миграцию или безопасно записать файл, но не решает, какие проекты допустимы и что является journal outcome.

Внутри маленького модуля достаточно нескольких файлов выше. `domain/`, `use-cases/`, `ports/` выделяются при реальной необходимости, а не по шаблону. Связанные короткие функции могут жить вместе; один файл на каждую функцию так же нежелателен, как один файл на всё приложение.

## 6. Правила зависимостей и владения

```text
CLI → публичные сценарии приложения
app-сценарии → публичные API предметных модулей
сценарий модуля → его модель + его порты
адаптер модуля → его порты + техническая infrastructure
модель → только чистые общие типы
```

Стрелки означают разрешённые зависимости, а не каждую runtime-передачу управления. При вызове эффекта сценарий использует переданный порт; конкретная реализация выбирается в `create-app.ts`.

- Только composition root собирает конкретные адаптеры и передаёт зависимости обычными аргументами/factory. Это явное исключение для доступа к adapters, не разрешение обхода границ из любого app-файла.
- Соседние модули не импортируют внутренние файлы друг друга. В M1 межмодульную координацию держим в app; общий `scope` содержит форму/валидацию значения, а проверка регистрации проекта остаётся в projects.
- Порт принадлежит потребителю. Он описывает нужную операцию, не экспортирует соединение SQL, Node streams или объекты стороннего драйвера в доменную модель.
- Модули отвечают за свои данные; чужие таблицы не читаются напрямую, даже если физически БД одна. Общая последовательность миграций не отменяет этого владения.
- Warmup может собирать read model из нескольких публичных API без копирования правил наследования memory и без неявной записи.
- DB-only транзакция и смешанная DB/files/git операция — разные контракты. Координация и recovery располагаются в app с нужными портами; физические операции — в адаптерах. Разделение по папкам само не делает их атомарными.
- Импорт модулей не выполняет IO. `process.exit`, `argv`, stdout/stderr находятся на CLI-границе; environment и paths разрешаются при сборке приложения, не читаются из каждого модуля.
- Domain-модель не импортирует filesystem, Git, DB или CLI. Production-код не импортирует `test/` и `scripts/`.

## 7. Роль scripts и защита от больших файлов

`src/` — продукт. Пользовательские команды bootstrap/backup/recovery реализуются там и используют тот же API, что и основной CLI. `scripts/` — только технические запускатели build/проверок и небольшие инструменты сопровождения. Не должно быть отдельной версии доменной логики «для скрипта».

В scripts нет продуктового CLI или bootstrap. Единственный исполняемый вход продукта — Node.js CLI в src/cli; старый прототип и импорт его данных удалены.

Что проверять механически после разрешения реализации:

- разрешённые направления импортов, отсутствие циклов и обращений к внутренностям соседних модулей;
- запрет инфраструктурных зависимостей в моделях и CLI-вывода внутри модулей;
- production не зависит от tests/scripts;
- соблюдение профилей и ресурсов из TESTING.md.

Использовать готовую проверку импортов/зависимостей, не собственный архитектурный framework. Для TypeScript-импортов выбран dependency-cruiser; проверка импортов не доказывает отсутствие всех динамических эффектов.

Размер файла — сигнал review, но не единственный критерий. Численный порог пока не выбран. Файл разделяется, когда смешивает разные причины изменения: например, parsing argv, правило доступа, SQL и формат stdout. Не дробить связное поведение на десятки forwarding-функций ради прохождения лимита строк. Не выносить всё в `utils.ts`, `common-service.ts` или `manager.ts`.

Проверка архитектуры через обычное изменение: новое правило note должно в основном менять knowledge и его тесты; замена Git-вызова — Git adapter; добавление будущего Pi-входа — новый входной адаптер, не копию бизнес-логики.

## 8. Связь с тестовой политикой

Модули дают дешёвые публичные API для fast-тестов. Реальные temp FS/embedded DB проверки возможны без запуска CLI, если укладываются в TESTING.md. В boundary остаются настоящие launcher/Git/restart и другие необходимые процессные границы.

Отделение эффектов не требует повсеместных mocks. Проверяется реальное поведение; mocks не становятся копией SQL/filesystem. Нет отдельного runner на модуль, вложенных test suites или обязательного теста на каждый внутренний helper.

## 9. Запись подготовки

Историческая запись до выбора архитектуры; последующее подтверждение — §10.

Принято требование pnpm; предложены варианты архитектуры и рекомендуемая структура в `docs/M1-DESIGN.md`. Основание анализа — компоненты M0/ARCHITECTURE, TESTING и текущий legacy CLI, где функции совмещают проверку правил, IO и вывод. Выбор варианта ещё не подтверждён; каталоги исходников и тестов не создавались, зависимости не устанавливались, код и личные данные не менялись. `home/` отсутствует; исход сохранён здесь, без инициализации личного хранилища.

Проверка документации: Node.js-скрипт проверил 15 документов, 58 локальных ссылок, code fences/пробелы, фиксацию pnpm и статус архитектурного предложения. `git diff --check` и `git diff --exit-code -- scripts/ .gitignore` прошли. Это проверка документов, не работающих модульных границ или сборки.
