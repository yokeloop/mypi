# ADR-0002: Плагины-сабагенты поверх примитивов Pi

Статус: **proposed** (зафиксировано по решению инженера от 2026-09-25;
фаза 4, реализация после стабилизации фаз 2–3).

Дата исходного предложения: 2026-09-25

## Уточнение M0 — 2026-09-29

См. [M0-CONTRACT](../docs/M0-CONTRACT.md) и [ARCHITECTURE](../docs/ARCHITECTURE.md).
Исходное предложение ниже сохранено; прежняя нумерация/зависимость фаз не действует.

- Первая поставка — память и проекты на Node.js с состоянием в БД, без
  flow и сабагентов. Юниты создаются позднее по задачам инженера.
- Принятый инженером термин — **unit / юнит**.
  Юнит содержит роль, интерфейс, ограничения и **собственную политику
  приёмки**: кто/что принимает результат. Flow выбирает и связывает юниты;
  runtime проверяет контракт и фиксирует результат в БД. Human-only правила нет.
- Пример Pi, кастомный runner yokemate и отдельный pi-subagents — разные
  реализации. Утверждения ниже о «готовых» guards/acceptance/cleanup требуют
  проверки выбранной версии; название «официальный пакет» здесь не доказано.
- JSON stdout — поток результата/событий, не двусторонний канал управления;
  chain не даёт произвольный loop/recovery автоматически.
- Tools/cwd и декларативный prompt не являются sandbox; scripts/extensions
  исполняют код. Runtime и контракт прав проверяются до доверия чужому юниту.
- Status hook относится к разрешённой доменной операции через общий Node core;
  изменение MD/git pull само не запускает flow. Оперативное состояние — в БД.

Точный формат юнита, runner и DSL остаются proposed; они не блокируют M1.
Исходное исследование ниже — provenance, не гарантия нового runtime.

## Контекст

Исходная идея mypi: подключаемые сабагенты как модули (инструкции + скрипты +
конфиг pi-агента), конфиг-флоу на каждый проект (статус↔сабагент, массив шагов,
луп, правила переходов, сейфгарды на уровне плагина). Требовалось понять, как
Pi запускает сабагентов и как ими управляет. Исследование проведено по коду
yokemate-pi (`.pi/extensions/subagent/`) — продакшн-интеграции, не по докам.

## Как Pi запускает сабагента (проверено кодом yokemate-pi)

Сабагент — отдельный процесс `pi` CLI, не внутренняя сущность:

```
pi --mode json -p --no-session \
   [--model <m>] [--thinking <level>] \
   [--tools <read,bash,...>] \
   --append-system-prompt <tmp-файл> \
   "Task: <текст>"
```

- `--mode json` — JSON-стрим в stdout; родитель парсит события построчно,
  собирает messages и usage (tokens, cost, turns). Это канал управления.
- `-p` + `--no-session` — one-shot, изолированный контекст, без сессии.
- `--model` — модель на запуск; если в конфиге агента модели нет, наследуется
  dispatch-конфиг родителя (+ `--thinking`).
- `--tools` — белый список инструментов = механизм прав (сейфгарды).
- `--append-system-prompt <файл>` — system prompt агента (его роль) пишется
  во временный файл и подкладывается поверх дефолтного.
- `cwd` — процесс запускается в указанной директории (worktree, home).
- `HERDR_PANE_ID` вычищается из env ребёнка.

## Определение агента — Markdown-файл

`.pi/agents/*.md` (project) или юзер-директория:

```markdown
---
name: task-executor
description: Implements a plan step by step
tools: read, bash, edit      # или [read, bash, edit]
model: gpt-6-astra           # опционально
---
<system prompt — тело файла>
```

Discovery — скан папки + YAML frontmatter. **Добавить агента = положить
файл.** Роль, права, модель — всё в одном файле.

## Режимы dispatch

- **Single**: `{agent, task}` — один запуск.
- **Parallel**: `{tasks: [...]}` — батч; лимиты из `.pi/settings.json`
  (`subagent.maxParallelTasks: 8, maxConcurrency: 4, maxDetached: 8`;
  набор лимитов принимается целиком или отбрасывается целиком).
- **Chain**: `{chain: [...]}` — последовательность; в задачу следующего
  шага подставляется результат предыдущего через плейсхолдер `{previous}`.
  **Это готовый примитив «массив и луп сабагентов».**

## Управление жизнью процесса

- `AbortSignal` тул-колла убивает ребёнка вместе с отменённым turn.
- Detached-реестр (`Set<ChildProcess>`) — вызовы, переживающие тул-колл;
  убивает только конец сессии (cleanup на `session_shutdown`); флаг
  `shuttingDown` закрывает очередь батча, `turn_start` снимает.
- Batch-счётчик (`activeUnits`, `batches`) — сколько поднято/осело; счёт
  синхронный, чтобы модель не врала о полноте набора.
- `runningAgents`-реестр — живой виджет «кто работает и сколько».

## Важно: исправление по официальному пакету pi-subagents

Первоначальный разбор вёл по кастомному расширению yokemate-pi
(`.pi/extensions/subagent/`). Официальный пакет `pi-subagents` (v0.55)
сильнее: у него ЕСТЬ `allowedAgents` (allowlist имён запускаемых детей),
рекурсивный discovery подпапок, `permission: allow|ask|deny` per-tool
(one-call arbiter, fail-closed), launch rules по моделям, watchdog,
acceptance gates, recursion guard (default depth 2), workflowScript с
бюджетами, per-agent persistent memory. Полный справочник:
`references/pi-subagents-reference.md`. Для фазы 4 это готовые примитивы:
поля `dispatch.allowed` из решений ниже заменяются штатным `allowedAgents`,
сейфгарды — штатным `permission: ask`.

## Решение: архитектура плагина поверх примитивов

```
<plugin>/
├── agent.md          # роль: frontmatter (name, description, tools, model) + system prompt
├── scripts/          # вспомогательные скрипты, доступные агенту через bash
└── config.yaml       # сейфгарды, условия запуска, формат выхода
```

Конфиг-флоу проекта = **компиляция в dispatch-план**: секция конфига
«статус → агент» разворачивается оркестратором в `{chain: [{agent, task},
...]}` / `{tasks: [...]}` с параметрами. Вложенный граф сабагентов — агент,
у которого есть свой subagent-тул; право на dispatch задаётся через его
`tools` (вложенность ограничивается на уровне плагина, как в исходной идее).

Таблица соответствия «поле конфига → флаг/примитив pi»:

| Поле конфига проекта | Примитив Pi |
|---|---|
| agent (роль, system prompt) | `--append-system-prompt <файл>` |
| tools / права / сейфгарды | `--tools <список>` |
| model на шаг | `--model`, `--thinking` |
| рабочая директория шага | `cwd` спавна |
| последовательность шагов | `chain` + плейсхолдер `{previous}` |
| параллельные шаги | `tasks` (parallel) + `maxConcurrency` |
| лимиты | `.pi/settings.json` `subagent.*` |
| вложенный граф | subagent-тул в `tools` агента |
| контроль результата | `--mode json` (usage, messages, exit code) |
| остановка | AbortSignal / detached-реестр |

## Что нужно написать своё

1. **Интерпретатор конфига** — YAML → dispatch-план (chain/parallel с
   параметрами, правила переходов, сейфгарды).
2. **Хук статусов** — «статус request сменился → запусти flow из конфига
   проекта» (связка с ADR-0001: request lifecycle в фазе 2).

Spawn, права, модели, chain, лимиты, убийство, detached — Pi уже умеет.

## Следствия

- Плагин = данные (md + yaml + скрипты), не код оркестратора. Регистрация
  нового плагина — копирование папки, как agенты в `.pi/agents/`.
- Конфиг-флоу проекта не исполняется сам: его читает оркестратор mypi и
  компилирует в dispatch-вызовы Pi. Единая точка исполнения = единая точка
  сейфгардов.
- Модель на шаг переопределяет модель паспорта проекта (как `--model` бьёт
  дефолт в yokemate).
