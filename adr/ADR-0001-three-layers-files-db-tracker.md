# ADR-0001: Три слоя данных — файлы как правда, БД как оперативный слой, tracker как проекция

Статус: **proposed** (зафиксировано по решению инженера от 2026-09-25; фаза 2+,
дальнейшая проработка отложена — «еще подумаем над этим потом»).

Дата исходного предложения: 2026-09-25

## Уточнение M0 — 2026-09-29

Ниже сохранён срез M0. Позднее при подготовке M1 выбраны SQLite и `better-sqlite3` — [запись принятия стека](../docs/M1-DESIGN.md#11-принятие-стека); это не принятие исходного ADR целиком.

Принятые инженером границы данных зафиксированы в
[M0-CONTRACT](../docs/M0-CONTRACT.md); исходный ADR не принят целиком.

1. **БД — источник истины для управляемого состояния с начала новой
   реализации.** Не кэш, не seed из requests.md, не проекция frontmatter.
2. **Файлы — контекст и знания агентов:** память, glossary, заметки, исходы,
   адресуемые артефакты. Они не заменяют DB backup и не содержат весь прогресс.
3. **Первый runtime — Node.js, первая поставка — память и проекты.**
   Multi-device, request lifecycle, flow и tracker не обязательны. SQLite
   рекомендован для локальной БД; движок инженером пока не выбран.
4. Локальный git commit контекстных файлов автоматический, сеть разрешается
   отдельно. Инженер уточнил Q5: БД в git не хранится; DB-only операции —
   DB-транзакция, backup отдельно. Git+SQL не одна атомарная транзакция;
   механизм cross-store recovery проектируется в M1.
5. Приёмку будущей работы определяет юнит (`unit`) и выбранный flow. Список
   статусов и обязательная human acceptance не фиксируются глобально сейчас.
6. Tracker update остаётся явно разрешённым внешним действием, не автоматическим
   следствием done; журнал исходов не дублирует каждый DB-переход.

**Исходный текст ниже — историческое proposed-решение, частично заменённое
этим уточнением.** Его обещания восстановления состояния только из MD,
отсутствия конфликтов у одного инженера, атомарности git+DB и обязательный
порядок фаз больше не являются требованиями. Прежнее обоснование сохранено.

## Контекст

Фаза 1 mypi закрыла second brain: `home/<org>/<project>/` — журналы, память
(global/org/project), глоссарии, артефакты, паспорт. Дальше — привязка БД
статусов и ведение тикетов. Требуется учесть опыт старой реализации
(yokemate-pi) и контракты NorthStar.

## Решение

Три слоя, у каждого своя работа:

1. **Файлы (git) — источник истины для знаний.** Request — не строка в БД, а
   Markdown-файл `home/<org>/<project>/requests/<id>.md` с frontmatter
   (status, links, related, created). Git даёт: историю в диффах, ревью,
   поиск, иммутабельность артефактов.
2. **БД — живое состояние, проекция.** Только то, что нужно между
   устройствами в реальном времени: текущий статус, связи, очередь.
   PostgreSQL как single authoritative store (рекомендация NorthStar
   roadmap: никакого multi-master, никакого синка mutable SQLite через git).
   Стёрлась БД — состояние восстанавливается из requests-файлов;
   стёрся git — БД бесполезна.
3. **Tracker — интеграция, не корень.** Тикет — проекция request наружу
   (команда видит в YouTrack/GitHub), lifecycle живёт в mypi. Импорт issue →
   draft по явной команде; request done → обновление тикета. Односторонне
   в каждую сторону, явно. Тикет никогда не обязательное условие начала
   работы (инвариант NorthStar против боли старой ticket-driven системы).

## Что берём из старой реализации (yokemate-pi)

- **Sync в момент действия:** pull когда нужно, push после изменения.
  Никаких фоновых демонов репликации. Для соло-использования конфликты
  статусов не существуют.
- **Локальная БД как проекция** для быстрых запросов, не источник истины.

## Что берём из NorthStar

- Request lifecycle: Draft → Backlog → Planning → Shipping{Doing/Review/
  Deploying} → Acceptance → Done (+ Canceled/Archived, терминальные
  статусы не reopen-ятся).
- Explicit capture: обычное сообщение ничего не создаёт; enqueue — осознанный шаг.
- Смена статуса автоматически пишет outcome-строку в журнал проекта
  (проверенный паттерн yokemate).

## Что НЕ берём (пока)

Ownership, leases, fencing, handoff между координаторами. Вся сложность
NorthStar-темы 2 существует из-за множества координаторов и агентов.
У нас один инженер и одно устройство за раз. Claims/leases появятся в БД
в фазе 4+ вместе с сабагентами — NorthStar уже спроектировал, как.

## Порядок внедрения

1. **Фаза 2 — lifecycle в файлах, без БД:** `request new|status|list`,
   state machine с валидацией переходов в CLI, автозапись исходов в журнал,
   `tracker` в паспорте, `request import` (issue → draft). Контракт
   проверяется руками на git-истории, задарма.
2. **Фаза 3 — PostgreSQL под статусами:** схема = frontmatter requests-файлов
   (id, title, status, org/project, links, related, created/updated/closed);
   файлы — seed-данные, миграция механическая. CLI-интерфейс не меняется,
   меняется backend. Синк — в момент действия: команда = commit в git +
   транзакция в БД.
3. **Фаза 4+ — сабагенты/табы:** таблица `claims(request_id, owner,
   lease_until)`, NorthStar-контракты ownership становятся инструкцией
   к реализации.

## Следствия

- БД не покупается раньше, чем доказан файловый контракт.
- Формат frontmatter requests — будущая схема БД: то, что в файле,
  то и в таблице.
- Tracker-интеграции добавляются после того, как lifecycle стабилен
  в файлах.

## Открытые вопросы (отложены)

- Схема связей related/links: id-формат, глубина графа.
- Где живёт очередь приоритетов: файлы, БД или паспорт.
- Двусторонний sync с YouTrack или только односторонние проекции.
