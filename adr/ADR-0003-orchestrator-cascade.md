# ADR-0003: Каскад оркестраторов — root / org / project

Статус: **proposed** (зафиксировано по решению инженера от 2026-09-25;
решения на фактах, систему не строим — реализация после фаз 2–3, частично фаза 4–5).

Дата: 2026-09-25

## Контекст

Требуется слой оркестраторов с учётом структуры mypi: корневой оркестратор,
оркестратор по организации, оркестратор по проекту. Основание — факты из
yokemate-pi (код, продакшн), NorthStar (контракты) и уже принятых ADR-0001/0002.

## Решения (на фактах)

### 1. Оркестраторы ложатся на существующий каскад скоупов

Уровни оркестраторов = уровни памяти (global/org/project). Контекст
оркестратора скоупа X = `warmup -s X` + конфиг уровня X. Вход в скоуп уже
реализован; новый слой сущностей не вводится.

### 2. Оркестратор — тот же формат агента, что и сабагент (ADR-0002)

Факт yokemate: «главный чат» и сабагент — один примитив, pi-процесс с
system prompt + tools + model. Разница оркестратора и воркера — только
конфигурация:

- worker: `tools: [read, bash, edit]` — предметная работа, без права dispatch;
- orchestrator: `tools: [..., subagent]` — право поднимать других.

Иерархия: root-оркестратор поднимает org-оркестраторов; org — project-оркестраторов;
project — воркеров. Вложенность графа = право `subagent` в tools (как в
исходной идее: ограничения определяются на уровне плагина).

**Следствие:** слой оркестратора — не новый код, а конфигурация поверх
механизма ADR-0002. Регистрация оркестратора = agent.md-файл.

### 3. Ownership = дерево процессов

NorthStar проектирует leases/fencing/handoff, потому что его координаторы —
пиры (любой может взять любой request → гонки). У нас иерархия root → org →
project → workers, и дерево процессов в Pi уже даёт ownership-семантику:

- родитель владеет жизнью ребёнка (AbortSignal; смерть родителя убивает
  детей — проверено кодом yokemate);
- detached — исключение, требующее реестра (паттерн yokemate: detached-Set,
  cleanup на session_shutdown);
- два оркестратора одного проекта не существуют без общего родителя.

Пока структура иерархична, leases не нужны. Они станут нужны при пирах
(две машины поднимают project-оркестратора) — фаза 5, контракты NorthStar
(тема 2) там уже спроектированы.

### 4. Размещение конфигов: движок vs данные

- root-оркестратор: конфиг в движке (репо mypi) — общий, версионируется
  с кодом;
- org/project-оркестраторы: конфигы = данные, `home/<org>/AGENTS.md` и
  `home/<org>/<project>/AGENTS.md` — синк через git, кастомизация
  per-project (исходная идея: «кастомные инструкции и флоу под каждый
  проект в виде конфиг файла»).

### 5. Коммуникация: человек-как-шина (фазы 2–4)

Факт yokemate: courtesy-сообщения + unix socket ACK, и сам же код
комментирует: ACK — не durable очередь (слабость задокументирована).
Факт NorthStar: проектирует inbox/outbox с ack.

Решение на фазы 2–4: **никакой межагентной очереди**. Результат ребёнка
возвращается родителю через stdout (`--mode json`); между сессиями —
файлы в home/ (журнал, requests). Человек — шина между оркестраторами
разных сессий. Межоркестраторный транспорт — фаза 5, сверять с NorthStar.

## Соответствие NorthStar

- «Координатор не выполняет предметную работу» — наследуется: у
  оркестраторов нет предметных tools, только dispatch + память/журнал.
- «Один grill на coordinator chat» — оркестратор уровня держит один
  активный диалог своего уровня.
- Ownership/leases/handoff — НЕ наследуется (иерархия вместо пиров,
  см. решение 3); пересмотр при появлении пиров.

## Ограничения диспетчера (факты из кода yokemate, схема SubagentParams)

- **Каких сабагентов можно запускать:** встроенного allowlist по именам нет.
  Существующие механизмы: `agentScope` (user|project|both — фильтр по
  директориям-источникам определений: `~/.pi/agents/` vs `.pi/agents/` в
  cwd; НЕ ограничение доступа), `tools` (бинарное право subagent-тула),
  `confirmProjectAgents` (подтверждение проект-локальных агентов).
  Решение mypi: пул агентов общий для всех проектов и орг
  (`agentScope: user`), проект не «владеет» агентами, а выбирает их из
  пула в своём конфиге флоу. Allowlist права диспетчера — поле
  `dispatch.allowed` в agent.md; enforcement — наш интерпретатор
  (ADR-0002), единственная точка spawn. Надёжнее промпта, потому что
  техническая.
- **Область оркестратора:** `cwd` spawn (параметр каждого TaskItem/ChainItem)
  ограничивает контекст: org-оркестратор → `cwd=home/<org>/`, project →
  `home/<org>/<project>/`; Pi грузит конфиги из дерева cwd + каскадный
  `warmup -s`. Но это софт-граница: у Pi нет filesystem-sandbox, `bash` может
  выйти за cwd. Хард-периметр — уровень ОС (контейнеры; ср. NorthStar
  fermi + sandbox playbooks). Рамка изоляции: tools > cwd+конфиг > промпт.
- **Интерактивность:** сабагент запускается либо headless (`--mode json -p
  --no-session`), либо табом/split (как herdr-табы yokemate) — определяется
  конфигом плагина, не кодом.

## Открытые вопросы (отложены)

- Формат конфига флоу (секции vs список шагов) — отложено в ADR-0002.
- Плагины org-уровня: где живут и что наследуется от root.
- Правила «когда project-оркестратору можно поднять второго воркера» —
  вместе с сейфгардами ADR-0002.
- Хард-периметр (контейнеры) — при появлении реального sandbox-требования,
  фаза 5+.
